# Risk assessment of the app's derived low-level requirements

The app's first architecture ledger
(`apps/desktop/docs/architecture/2026-10-05-decomposition.md`,
this change) writes forty-six low-level requirements. Thirty-three refine a
high-level requirement that the risk register has already assessed, and they
inherit that assessment unchanged. **Thirteen are `satisfies: derived`**: they
record behaviour that no requirement demands. ISO 14971 asks that such
behaviour be assessed rather than assumed harmless, and this file is that
assessment.

Counted 2026-10-05 against the draft: `grep -c '^\*\*LLR-'` is 46 and
`grep -c '^satisfies: derived'` is 13. Recounted after review round 2
(finding-4): review round 1 added LLR-uus6ar, which refines REQ-cj5jmx.

The hazards named below are those of `apps/desktop/docs/risk/2026-09-14-app-hazards.md`
§4, with the method and the acceptability matrix of that file and of
`apps/desktop/docs/risk/README.md`. **No new hazard and no new risk control** is
introduced. Each section says why, and where a derived requirement pins
behaviour that an open problem report calls a defect, it names the report.

## The transport mode's parsing

assesses: LLR-j5pacp

Assessed against **HAZ-n97v5g**. A misspelled `ODS_TRANSPORT`, such as
`LOOPBACK` or `loop back`, yields Networked, silently. The mode the service
runs in and the mode it reports come from the same value (LLR-8tzbzn,
RC-8ygnjd), so the mode the app reports matches what the service does. An operator who meant Loopback is
shown Networked in the status bar. The mapping adds no path to the hazard's
harm. It is the behaviour the register was assessed against, which
`transport_mode_from` was written to preserve exactly.

## What a persona carries across IPC

assesses: LLR-pguhw5

Assessed against **HAZ-8ghmhn**'s family: the confidentiality of key
material. The persona object that crosses into the webview has exactly six
fields and no seed. That bounds what a script in the webview could read
through `list_personas`. This matters more since HAZ-e2zupz showed that a
script there can call every command. No new hazard: the requirement narrows
an exposure and opens none.

## The shared org-io handle

assesses: LLR-5wb4vd

Added 2026-10-14 (change `worktree-org-io-transport`, S4 task T16).
Assessed against concurrent access to the node's state and store. Removing
the app's lock does not leave that state unguarded: org-io holds org-node
behind its own lock, takes it for each of its operations, and releases it
only while waiting for a message or reading the chain (org-io's requirement
that the receive loop hold no lock while it waits), so two commands, or a
command and the receiver, never act on the node at once. What changes is
that a command no longer waits for a message to arrive, the defect of the
receiver holding the lock (org-io's problem report, resolved there).
Against HAZ-cfp4jb: the receiver loop's termination is still
announced and its slot still released (REQ-jfxah3, REQ-3hfggn), and its
clone of the handle is dropped with the task. No new hazard and no new risk
control.

## The three events of a verified update

assesses: LLR-p2nm5a

Assessed against **HAZ-9fmhm4** and **HAZ-5ha5vv**. Each value is the measured
one, epoch 0 included, so no sentinel reaches the display (HAZ-5ha5vv). But
`membership-updated` and `incoming-verified` carry the same update, and
Membership.svelte files both as verification rows, so one verified update is
shown as two. That overstates the count of verifications, which is HAZ-9fmhm4's
territory. It is not new: it is booked as PR-bu6mau, and that report carries
the hazard note. This requirement records the mapping as it is and does not
make the duplicate a requirement of the display.

## The placeholder for an unnamed organisation

assesses: LLR-mzae5q

Assessed against **HAZ-9fmhm4**. A failure that names no organisation is shown
as `(unknown organisation)` rather than `null`. Every such failure today is
unnamed (LLR-wgr46u), so the row cannot say which organisation failed. That is
PR-j9f6kk's item 1, open and unchanged. The requirement records today's
behaviour, and the row's outcome stays "not verified" (REQ-a83vqr). No new
hazard.

## The two list limits

assesses: LLR-rzx6ks

Assessed against **HAZ-9fmhm4**, through the verification log as the
operator's record. The log keeps the newest 50 rows and the error list the
newest 20. Older entries are dropped from the view and are not persisted
anywhere, so a burst of more than 50 verifications hides the earliest from the
operator. The register already identifies this as unminted control 11 of its
§8 ("a display cap rather than a retention policy"), and it stays unminted.
The bound protects the webview's memory, and the log is not the system of
record: the chain is. The bound was in the code the register was assessed
against; this requirement only makes it gated. No new hazard.
