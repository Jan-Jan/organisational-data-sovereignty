## SDD-789u6d — Custody of the user's signatory key

`crates/org-io/src/custody.rs`: `ConfigError`, `ConfigVariable`, `ConfigRule`,
`parse_seed`, `parse_co_signer`, `SeedBytes`, `SignatoryKey`, and, under the
`dev-seed` feature only, `signatory_from_environment`.

**SDD-789u6d**: the user's own sr25519 signatory key and its development
configuration: reading `ODS_ADMIN_SEED` (development builds only), parsing it
and the co-signer value with total functions whose errors carry no part of
the value, building the key, and holding it so that nothing outside org-io
can obtain it or see it rendered.
traces: REQ-3pxa8f, REQ-v4tfap, REQ-8zuka3, REQ-qnh9pb

**LLR-4ax2m6**: `parse_seed(raw: &str) -> Result<SeedBytes, ConfigError>`
removes at most one leading `0x` and accepts the rest exactly when it is 64
characters of `0-9a-fA-F`, returning its 32 bytes; it refuses an empty
value, any other length, any character outside that alphabet (a second
`0x` included) with `ConfigError { variable: AdminSeed, rule }`, and panics
on no input.
satisfies: REQ-qnh9pb

Test: `crates/org-io/tests/key_custody_config.rs` (normal: 64 hex with and without
one `0x`, upper and lower case, give the same bytes; abnormal: empty, 63, 65,
`0x0x` + 64, a non-hex character, non-ASCII input) and
`crates/org-io/tests/fuzz_seed_parse/fuzz_target.rs` (no panic on any byte string).

**LLR-9fy622**: `parse_co_signer(raw: &str) -> Result<AccountId, ConfigError>`
applies the same single strip and accepts exactly 64 hexadecimal characters,
returning the 32-byte account; any other input is refused with
`ConfigError { variable: CoSigner, rule }`, and no input panics. An absent
co-signer value (`None` handed in by the app) means no co-signers.
satisfies: REQ-qnh9pb

Test: `crates/org-io/tests/key_custody_config.rs`, `crates/org-io/tests/fuzz_seed_parse/fuzz_target.rs`.

**LLR-gc6kwy**: `ConfigError` holds only a `ConfigVariable` (`AdminSeed`,
`CoSigner`) and a `ConfigRule` (`Empty`, `NotHex`, `WrongLength`,
`NotAKey`), no string and no byte taken from the input; its `Display`
names the environment variable and the rule (for example
`ODS_ADMIN_SEED must be 64 hexadecimal characters after at most one leading 0x`)
and its `Debug` is derived from those two enums, so neither rendering can
contain any part of the value parsed.
satisfies: REQ-qnh9pb, REQ-v4tfap

Test: `crates/org-io/tests/key_custody_config.rs` (every abnormal case asserts that
neither rendering contains any four-character window of the stripped input)
and `crates/org-io/tests/fuzz_seed_parse/fuzz_target.rs` (the same assertion on
arbitrary input of at least four characters).

**LLR-c4bktx**: `SignatoryKey` holds the sr25519 key pair in a private
field; it offers `account_id() -> AccountId` (the public key) and no public
operation that returns the key pair, the seed or any secret bytes; the
writer reaches the key pair only through a `pub(crate)` accessor. Its
`Debug` is written by hand and renders `SignatoryKey(account ` followed by
the first four bytes of the public key in lower-case hex and `..)`; it has
no `Display`. `SeedBytes` holds the 32 seed bytes, wipes them on drop

satisfies: REQ-3pxa8f, REQ-v4tfap

Test: `crates/org-io/tests/signatory_key.rs` (normal: the account of a known seed;
abnormal: `format!("{:?}", key)` and `format!("{:?}", seed)` contain no
four-character window of the seed's hex).

### The item with no low-level requirements

SDD-z85ux9 carries none, under a class that requires them. This section is the
deviation, recorded here rather than left for a reader to notice.

**What it is not.** The `on-chain-client` unit has an item of the same shape —
its chain-facing transport shell, the one item its decomposition records as
carrying no low-level requirements, described in the section "The item with no
low-level requirements" of
`crates/on-chain-client/docs/architecture/2026-09-28-decomposition.md` — and **its
argument does not transfer.** That item is *unreachable*: nothing exercises it
at all. This one is exercised, by the chopsticks target `crates/org-io/tests/preflight.rs`
(the chain.live check, stalled and mined), moved with it from org-node.

**What it is.** That target is excluded from this unit's `verify_commands`,
by a decision recorded in `crates/org-io/.guardrails/config.yaml`: it spawns a
chopsticks fork and needs `contracts/scripts/node_modules`, neither of which
the gate provides. So the honest statement is narrower than
on-chain-client's, and worse:

> A low-level requirement written here could be true, could be well-tested, and
> **no mutation to the code it describes would redden this unit's gate.** It
> would be an assertion carrying no evidence that this gate can produce.

That is the failure this repository has recorded more than once — a property
credited to an assertion that cannot observe it — and writing LLRs into the
one part of the unit where the gate is blind would be committing it
deliberately.

**What follows from it.** The remedy is not to write the LLRs. It is to bring
the chopsticks target into the gate, which is an infrastructure change of its
own — a hermetic chopsticks fixture, or a recorded-transcript substitute for
the RPC layer — booked with the guardrails setup's own infrastructure work
rather than attempted here. What can be pinned without a chain is pinned: the read rule
(`read_org_state`, LLR-rm9x4z) is separated from `OnChainStateReader` by the
`RawStateSource` seam precisely so that it is gated.

*Note 2026-10-29 (change `worktree-org-io-domain-api`, conformance finding
T5-O5; owner ruling: accept and record):* the test in
`crates/org-io/tests/preflight.rs`, `chain_live_check_passes_with_miner_and_fails_when_stalled`,
