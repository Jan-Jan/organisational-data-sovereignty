# Problems found during change `worktree-org-io-publish-2`

Recorded 2026-11-09 from merge review round 1 (the last round) of change
`worktree-org-io-publish-2`, by dispatcher decision: the finding needs a rule
first, so it is filed here open and not fixed in this change.

**PR-gg4zwz**: `OrgService::removed_devices` lists a Device the current
record lists again, and nothing refuses re-admitting a revoked Device key.
affects: LLR-dsjht5, LLR-bgj2ff
opened: 2026-11-09
status: open

Found by merge review MR1 of change `worktree-org-io-publish-2` (org-node
finding-1, low; plan entry MR1-N1). `removed_devices`
(`crates/org-node/src/service.rs`) returns one view for every entry of
`revoked_devices`; it does not check that the current record no longer lists
that Device. LLR-dsjht5 returns each Device "the store holds as revoked
(LLR-bgj2ff)", and LLR-bgj2ff holds a Device as revoked only while
`revoked_devices` holds its DevicePublicKey *and the current record does not
list it*. `revoked_devices` is only ever appended to (`hold_dropped_devices`
in `crates/org-node/src/verify_org.rs`) and only `into_removed` drops it, and no
admission path reads it (the dispatcher checked: nothing refuses an
admission whose Device key `revoked_devices` holds). So a Device key admitted
again after its removal is still shown to the Admin as a removed Device. It
needs the same Device key re-admitted, which is rare; no test covers it.

Suggested fix: decide the rule first, then test it as an abnormal case of
LLR-dsjht5 and LLR-bgj2ff. Either refuse re-admitting a DevicePublicKey that
`revoked_devices` holds (an admission precondition, a new LLR), or drop the
entry from `revoked_devices` when an adopted record lists its Device again
(LLR-bgj2ff amended); in either case `removed_devices` filters with
`!record.lists_device(&revoked.device_key)` so it returns only the Devices
held as revoked.
