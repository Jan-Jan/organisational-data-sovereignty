# Design — the acknowledged record and the delivering Device (org-node)

Software item and low-level requirements for change
`worktree-org-io-publish-2`, task T13b (§0, owner rulings R1–R4 of
2026-11-02), drafted 2026-11-03 before any code, against master `7ac0825`.
They refine `crates/org-node/docs/requirements/2026-11-02-publish-2.md`. Every item
is class C, the unit's class, with no per-item override. No cross-unit edge
and no SOUP changes.

## Choices made (architecture, three options considered)

Where the acknowledged record lives:

1. **A field of `StoreData`, appended by the receive path** (chosen). The
   record is sealed with the rest of the Persona store, written by the store
   change `check_received` already returns and org-io already writes
   (org-io's receive step), and dropped by `into_removed` with everything else.
   No new file, no new org-io write path.
2. A separate sealed file per Persona, written by org-io. Rejected: a second
   file to keep in step with the store, for a record S5 replaces.
3. Kept by org-io in memory only. Rejected: REQ-h7y5ur keeps it across
   restarts.

How the removal learns its delivering Device:

1. **From what the store already keeps, plus the notice's sender** (chosen).
   A matched provisional organisation already keeps its `Origin` (`Received {
   from }`, `Answer { from }`); a kept revocation notice gains the `sender`
   the transport authenticated. No wire change.
2. Carry the sender in the notice body. Rejected: a Wire change for a value
   the transport already authenticates.
3. Ask org-io for the last connection's peer at removal time. Rejected:
   org-node holds no transport state, and the removal runs in verification,
   long after the receipt.

## The Persona store's fields (SDD-undd7q)

**LLR-f5wrjx**: `StoreData` holds, in this encoding order: `persona:
PersonaRecord`; `record: Option<OrgRecord>`; `org_name: String`;
`provisional_changes: Vec<ProvisionalChange>` in the order recorded;
`provisional_organisations: Vec<ProvisionalOrganisation>`; `founding:
Option<ProvisionalFounding>`; `member: Option<ProvisionalMember>`;
`kept_admission_requests: Vec<KeptAdmissionRequest>`;
`kept_revocation_notices: Vec<KeptNotice>`, each `KeptNotice { notice:
RevocationNotice, from: DevicePublicKey }` in that order (LLR-gb7p7c);
`expected_admissions: Vec<ExpectedAdmission>`; `outstanding_invites:
Vec<OutstandingInvite>` (as this item's earlier form stated them); `revoked_devices:
Vec<RevokedDevice>` (LLR-bgj2ff); `address_book: Vec<(DevicePublicKey,
EndpointAddresses)>` (LLR-h9d65p); `acknowledged:
Vec<AcknowledgedEntry>` (LLR-py43n3). Every field reaches the sealed
store and is read back unchanged by `PersonaStore::unseal`, except the
behind marker (LLR-zk7fx2); `KeptNotice.from` and the keys of each
`AcknowledgedEntry` are re-parsed with their types, a value the parse
refuses being `InvalidField` naming `org.kept_revocation_notices` or
`org.acknowledged`. A `StoreData` is sealed as the `Active` form of the
store plaintext (LLR-6zaeb6). A store in the format before this one does not
open.

## The receive path (SDD-busuj3)

**LLR-gb7p7c**: a revocation notice from a listed Device that
`revocation::check_notice` passes (LLR-r7zm39) is appended to
`kept_revocation_notices` as `KeptNotice { notice, from: sender }`, `sender`
the Device the transport authenticated for it (the bound applies), and
returned as `RevocationNoticeKept`; nothing is deleted and no secret is
asked for on receipt. A notice that comes in answer to this Device's
organisation request is a `Revocation` body like any other and is kept the
same way; only `verify` acts on it (LLR-jhy6t6), and `accepted_notice`
returns the first `KeptNotice`, in kept order, that `revocation::accept`
takes.
satisfies: REQ-ncv4sc, REQ-ea4qs5, REQ-2yduet, REQ-y9p27b, REQ-32cp7f

## The node's own removal (SDD-z4m57w)

**LLR-6fsnma**: the candidates for a removal are the distinct
DevicePublicKeys the member snapshots of the current record held before the
removal list, other than the Persona's own; with `n` of them, `k` is 3 when
`n` is five or more, 2 when three or four, 1 when one or two, and 0 when
none. The delivering Device is, on a removal by an adopted match, the `from`
of the match's `Origin` (`Received` or `Answer`; none for `Own`), and on a
removal by a notice, the `from` of the `KeptNotice` `accepted_notice`
returned (LLR-gb7p7c). When `k` is not zero and the delivering Device is a
candidate, it is the first recipient; the other recipients are the first
`k` − 1 of the remaining candidates, and with no delivering Device among the
candidates all `k` come from them, in this order: on a removal by a match,
first those the matched record still lists, then the others; on a removal by
a notice, all of them; each group in ascending order of the key's 32 bytes.
Each recipient is distinct, and its `recipient_addresses` are its
address-book entry (LLR-h9d65p), or `None` when the store keeps none for it.
satisfies: REQ-6tepxq, REQ-32cp7f

By the sender rule (LLR-283x6f) the delivering Device is listed by the
current record whenever a match or a notice reaches `verify`, so "is a
candidate" fails only for `Own` (no delivering Device) and for a delivering
Device equal to the Persona's own key, which the candidates exclude.
