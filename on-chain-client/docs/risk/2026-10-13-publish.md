# Risk analysis — mortal update writes and the pinned signatory-set read (on-chain-client)

Run 2026-10-08 for change `worktree-org-io-publish`, under IEC 62304 Class
C and the acceptability matrix in this ledger's README.

## Derived requirements assessment

**REQ-4aq8zh** (mortal update writes with a reported window): no new hazard;
it removes an unknowable. An immortal or default-mortal write the caller
cannot bound may execute at any later time, so a caller that stopped
waiting can never know whether it is safe to discard the update or write
again. With an explicit mortality from a known finalised block, the last
block of inclusion is known before the write, and a later finalised block
past it settles the question. The cost is availability: a write not
included within 64 blocks (minutes on a live chain) expires and must be
made again; it is reported, never assumed executed.

assesses: REQ-4aq8zh

**REQ-b8x2py** (one pinned read of the mapped account and its proxy
definitions): no hazard impact. The definitions feed a report, and the chain
itself enforces who may dispatch through the proxy; a value that does not
decode as the runtime's proxy definitions is a typed error, never read as "no
delegates", and the decoder bounds its allocation by the input's length, so a
hostile or corrupt value can neither panic the reader nor exhaust its memory.
It closes the gap of two reads each resolving its own finalised block: the two
values describe one finalised block.
The `Any` index comes from that block's metadata, never a constant, so a
runtime that renumbers its proxy types cannot make a restricted delegate
read as `Any`; a runtime with no `Any` variant is a typed error. Decoding
stays bounded and total, as before.

assesses: REQ-b8x2py
