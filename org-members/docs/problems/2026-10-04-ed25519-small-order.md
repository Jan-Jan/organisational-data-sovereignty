# Problem reports — ed25519 keys of small order and non-canonical encodings accepted

**PR-b7khyw**: org-members accepts a Member-as-a-group key or a device key that
is a small-order ed25519 point or a non-canonical encoding of a point, and a
device key that is a mixed-order (torsioned) point, a prime-order point plus a
non-identity small-order point. Its SOUP inventory states the opposite of the
first two: that `ed25519-dalek`'s `VerifyingKey::from_bytes` "rejects
non-canonical and small-order-subgroup encodings"
(`org-members/docs/architecture/soup.md`, `ed25519-dalek` row).
affects: REQ-shk82j, SDD-4yr9ge.
opened: 2026-10-04
status: resolved
resolution: root cause — org-members validated both keys through `VerifyingKey::from_bytes` alone; fixed 2026-10-05 by change `worktree-person-shared-types`, which validates them through `person`'s parse (LLR-z954wj, LLR-a645bx); tests `org-members/tests/device_key_decoding.rs` and `org-members/tests/member_key_decoding.rs`, where the non-canonical DevicePublicKey cases are refused but no test isolates the canonicity check (see the round 3 note below).

The resolution in detail. Resolved by the change on
`worktree-worktree-person-shared-types` (task branch
`worktree-worktree-person-shared-types-parse`). org-members'
devices are identified by `person::DevicePublicKey`, whose `parse` rejects all
three cases. `org-members/tests/device_key_decoding.rs` shows the public
constructor, and decoding a DevicePublicKey, a set of DevicePublicKeys, a member record
and a change set,
refusing a small-order point (the identity, y = 1), two non-canonical
encodings of it (the sign bit set with x = 0, and y = p + 1) and a mixed-order
point (a prime-order point plus the order-4 point y = 0). Each test first
asserts that `VerifyingKey::from_bytes` accepts the input. Run against the
pre-merge `person` (commit aff5e6b), the five tests failed and the
constructor accepted all four inputs. The SOUP row for `ed25519-dalek` is
corrected. The Member-as-a-group key half is resolved by LLR-a645bx (review
round 1, 2026-10-05): `org-members/tests/member_key_decoding.rs` shows the
same four entry points refusing libsodium's small-order u-coordinates and
the non-canonical p, p + 1 and 2^255 − 1, and accepting a twist u-coordinate;
run against master 05f6f04, where the key was still an ed25519
`VerifyingKey`, all eight tests failed. Review round 3 (2026-10-05) added the
four order-8 points, y = p − 1, y = p and an off-curve encoding to the
DevicePublicKey cases, and exact errors at every entry point.

*Noted 2026-10-05 by review round 3 (finding-10).* The non-canonical
DevicePublicKey cases are refused, but no test shows the canonicity check
refusing them, and none can. Every non-canonical encoding that
`VerifyingKey::from_bytes` decodes is also of small order or torsioned, so the
small-order and torsion checks refuse it too, and removing the canonicity
check changes no outcome (an equivalent mutant). LLR-z954wj's note records
the enumeration that shows it. The non-canonical half of this report is
therefore closed by the other two checks as much as by the canonicity check.

Found by the `person` unit's test `a_small_order_point_dalek_accepts_is_rejected`
(branch `worktree-person-unit`), which asserts that `VerifyingKey::from_bytes`
accepts the identity point (encoded as y = 1) and reports it with `is_weak()`,
and that `DevicePublicKey` rejects it; the independent review of
that change also found it accepts encodings with y ≥ p and x = 0 with the sign
bit set, so one point can be held under several byte strings. org-members'
`P2pMemberKey` and `P2pDeviceKey` validate through that call alone, so both
behaviours reach the membership record on master today, and the "every key
held once" rule, which compares encoded bytes, does not see two encodings of
one point as the same key.

The owner ruled (2026-10-04) that a `DevicePublicKey` rejects both
non-canonical encodings and small-order points, and (2026-10-05) that it also
rejects mixed-order points, a prime-order point plus a non-identity
small-order point, which `from_bytes` accepts and `is_weak()` does not report;
`person` implements the rules, and org-members' device keys accept all three
today. This report is resolved by the change that switches org-members to
`person`'s types (branch `worktree-worktree-person-shared-types`), which must
correct the SOUP row and show org-members' decode path refusing all three
cases for device keys. The three cases apply to device keys only: after the
switch the Member-as-a-group key is an X25519 `PersonPublicKey`, which rejects
small-order and non-canonical u-coordinates and, by the owner's decision,
accepts the u-coordinate of a mixed-order point.
