# Problems — gaps booked from S2's review

Recorded 2026-10-08 by the independent review of change
`worktree-org-io-create` (round 2, findings 3 and 7). The file is dated, not
a DRAFT, because that change's ledgers were already finalized when the
review ran.

**PR-8geawr**: `org_io::test_support::FakeChain` stands in for the chain write and the chain read on the normal path of every submission and receive test in org-io and the app, with no contract test tying its behaviour to `OnChainWriter`, `OnChainStateReader` or the contract.
affects: SDD-6qz9ms, SDD-erzj3m, SDD-z85ux9
opened: 2026-10-08
status: open

Where: `org-io/src/test_support.rs` (`FakeChain`). It is a fake, not a
stub: genesis returns `(org_id, proxy)`, `ChainSlots` does a compare-and-swap,
and it imitates the chain's errors (for example `InvalidOrgPublicKey`). The
owner accepted that the chain shell (SDD-z85ux9) is uncovered in S2; the
fake's fidelity to the real chain is a separate gap, which the test
checklist's test-double item requires to be stated. Fix: a contract test
that runs the same cases against `FakeChain` and the real
on-chain-client implementations, which comes with the chopsticks or
live-chain lane.

**PR-z3gg2b**: The app's IPC boundary property ("no IPC-facing type carries key material") is stated by no LLR and is checked only by an org-io test of the app's source, `no_ipc_facing_type_of_the_app_carries_key_material`, which finds carriers by type name only.
affects: REQ-v4tfap, RC-2xufsr, SDD-z3ychz
opened: 2026-10-08
status: open

Where: `org-io/tests/app_boundary.rs`. The test is annotated
`verifies: REQ-v4tfap, RC-2xufsr`, against the "lowest level present" rule
(LLR-3zdw8v and LLR-u2pk5y sit under REQ-v4tfap, and neither states the IPC
property), and it verifies another unit's source (the app's). It does not
recurse into the field types of a DTO, so a type alias or a nested non-DTO
struct holding `OrgPrivateKey` would pass, and it does not see hand-written
`Serialize` impls. Fix: an app-side LLR stating the IPC property, verified by
a structural test in the app.

**PR-wk7zwq**: REQ-f3eu9n and LLR-vyd5d3 count any proxy delegate equal to the controller as admin, ignoring the proxy definition's proxy type and delay, so a delegate that cannot dispatch `revive.call` through the proxy at once (a restricted proxy type, or a non-zero delay) is reported `Admin`.
affects: REQ-f3eu9n, LLR-vyd5d3, LLR-c9fyun, SDD-f4khqn
opened: 2026-10-08
status: open

Booked by round 3 of the same review (finding-4). Where: on-chain-client's
`decode_proxy_delegates` (`on-chain-client/src/write/signatory_set.rs`)
keeps only each definition's delegate account and drops its proxy type and
delay; org-io's `admin_status` then tests membership alone. Nothing acts on
the answer in S2 (the app is not wired to `OrgIo::is_own_admin`). S3b-io,
its first caller, must settle the rule (which proxy types and delays count
as admin) before relying on it; the fix then reaches both the decode in
on-chain-client and the rule in org-io.
