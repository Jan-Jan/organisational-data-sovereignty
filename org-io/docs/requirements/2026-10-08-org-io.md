# org-io: chain IO, key custody and the own-admin check (stage S2)

Change `worktree-org-io-create`, stage S2 of
`docs/plans/2026-10-06-org-io-roadmap.md`. Design:
`docs/adr/2026-10-06-org-io-unit.md` (Accepted 2026-10-08; Proposed when
this file was drafted) and
`docs/plans/2026-10-06-org-io-create.md`. Drafted 2026-10-06, before any code:
the crate lands in S2's develop phase, which waited for
`worktree-org-node-org-key-pair` (merged as `1f52c36`, reconciled here
2026-10-07). Until the crate's tests exist each requirement below is reported
MISSING-TEST, which is the truth.

These requirements cover what org-io does that no unit stated before: reading
the chain and handing org-node the values (ruling B, values in, values out),
the custody of the user's signatory key and the parse of its development
configuration, the own-admin check, and being the app's only way in. S2
changes no behaviour; where a requirement restates what the app or org-node
did, it says so.

**Two keys, kept apart** (owner, 2026-10-06):

- **The Organisation key pair** is Organisation-wide. It is the X25519 key
  pair the key-pair change introduced (merged as `1f52c36`;
  `org-node/docs/requirements/2026-10-07-org-key-pair.md`),
  held in org-node's Organisation record and used for encryption and key
  agreement only. It never signs anything, and it is outside S2's custody
  scope: nothing here holds, reads or parses it.
- **The signatory key** is one user's own sr25519 on-chain key. There is no
  Organisation-wide signing key. An Organisation's pure proxy is controlled
  by a multisig of its admins' own accounts, and a device is an admin's
  device when its user's account is one of those signatories. One user may
  be a signatory for several Organisations. This is the key org-io holds.

## Requirements

**REQ-tg9zrn**: The software shall, for every org-node operation that judges
against the chain, read the Organisation's state from the chain through
on-chain-client at the latest finalised block, parse it through org-node's
Organisation-state parse, and hand org-node the parsed state, or its absence
when the Organisation has no on-chain slot, as a value; when the read fails or
the parse refuses the state, it shall hand org-node nothing and report the
failure as an error, never as absence.
satisfies: derived

What this restates and what it changes. org-node read the chain itself,
through an asynchronous trait it awaited inside commit and verify; under
ruling B org-node takes the state as an argument and org-io does the read.
The commit after a chain write, verifying a received message, and the
revocation check all take their state this way. The parse stays org-node's,
so an Organisation public key that is not a valid X25519 key is refused by
org-node's rule and not by a copy of it. The finalised-block read is what the
moved expectation on on-chain-client asks for.

**REQ-f3eu9n**: The software shall report whether this node is an admin of an
Organisation: it shall read, through on-chain-client, the account the
Organisation's H160 maps to (`Revive.OriginalAccount`) and that account's
proxy delegates (`Proxy.Proxies`), and shall report the node an admin exactly
when one delegate equals the node's own chain account (no co-signers
configured) or the multisig account derived from the node's own account and
its configured co-signers at threshold 1; it shall report "not an admin" when
the H160 maps to no account or the account has no delegates, and shall report
a failed read as an error, never as "not an admin".
satisfies: derived
exported: yes

The chain can confirm a signatory set but cannot list one: pallet-multisig
stores no member list, because a multisig account is a hash. So this checks
the node's own status only, from its own key and configuration (accepted
recommendation, 2026-10-06), and nothing in S2 acts on the answer. Owner
ruling of 2026-10-07: S2 implements this in org-io, as `OrgIo::is_own_admin`
with its tests, and does not wire it into the app; nothing outside org-io's
tests calls it in S2. Its first caller is S3b-io (stage S3's org-io half).
The two storage reads are new on-chain-client reads, to be
written there as exported requirements; until they are, this unit may record
an `expects: on-chain-client` item for them.

**REQ-3pxa8f**: The software shall be the only holder of this device's
user's signatory key (the user's own sr25519 on-chain key, not the
Organisation's X25519 key pair): it shall obtain the key only through the
development path of REQ-8zuka3, keep it inside a type that offers no
operation returning the key or its bytes and whose `Debug` rendering shows
neither, and shall put neither the seed nor the key in any error, log line
or value it returns. (implements: RC-2xufsr)
exported: yes

What this changes. The app read the variable, built the sr25519 key pair and
kept it in its chain writer for the life of the process. After S2 the app
never sees the seed or the key. The app keeps reading the non-secret
configuration (`ODS_CHAIN_WS`, `ODS_CONTRACT_H160`) and hands it to org-io as
values.

**REQ-v4tfap**: The software shall never expose the user's sr25519 signatory
private key: not through any value it returns, error, log line, `Debug` or
`Display` rendering, message to the app over IPC, file, or the process
environment (beyond the development-only read of REQ-8zuka3); and it shall
neither receive nor output any device ed25519 private key: the Persona
store's device seeds stay inside org-node, and no public operation reachable
through org-io (its handle, `node()`, `node_mut()` or the `node`
re-export) hands out a device seed, a device key pair or anything that
yields one. (implements: RC-2xufsr)
exported: yes

*Narrowed 2026-10-08 (review round 1, finding 1).* The text said org-io
shall never "receive, hold or output" a device private key, "handling the
Persona store … only as opaque sealed bytes". In fact `OrgIo` owns the opened
`OrgService`, whose store holds the device seeds in memory, and until this
round org-node's public surface handed them out (`PersonaRecord`'s public
`device_seed`, a production `Serialize` on the store's records, and
`OrgEndpoint::inner()`, whose iroh `secret_key()` is the device key). The
output path is now closed in org-node; the in-memory hold stays until S4
moves the seeds to the OS keychain, and is not exposure. The rule is no
private key: device public keys, member keys, X25519 public keys and account
IDs may be handed out freely (owner clarification, 2026-10-08), and nothing
that returns one was restricted. Classification: a
narrowing (the "hold" and "opaque sealed bytes" clauses are withdrawn until
S4; the "never receive or output" clause is kept and now verified), so the
ID is kept. Verified by `org_node_hands_out_no_stored_device_private_key`
(org-io/tests/absences.rs, under LLR-3zdw8v).

*Clarified 2026-10-08 (review round 2, finding 1).* "No private key"
covers the X25519 secrets too: the Organisation private key and the Member
seed (the secret half of the Member-as-a-group key), which the text above
named only through "no private key". The output path through the handle's
`node()`/`node_mut()` and the `node` re-export is closed in org-node as for
the device seeds: `OrgRecord.org_private_key`, `PersonaRecord.member_seed`
and `ProvisionalUpdate.change` (which carries the next Organisation private
key) are crate-private, and `OrgRecord` and `ProvisionalUpdate` implement
`Serialize` only in test builds. The app never needed the Organisation
private key: it reads only public fields of the records. Public keys may
still be handed out. Classification under the hybrid rule: a
clarification (the owner's rule already said "no private key"; X25519
secrets are now named and checked), so the ID is kept. Verified by
`org_node_hands_out_no_stored_x25519_secret` (org-io/tests/absences.rs,
under LLR-3zdw8v).

*Clarified 2026-10-08 (review round 3, finding 1).* The handle's read
surface is an allowlist, not org-node's whole service. Name-based scans of
org-node's surface missed a path twice: `node()` returned `&OrgService`,
whose `endpoint()` reached `OrgEndpoint::recv_one`, which returns a
`WireMessage` carrying the next epoch's Organisation private key. `node()`
is gone. `OrgIo::view()` and `NodeBuilders::view()` return a `NodeView`,
whose methods return public data only (`PersonaSummary`, `OrgSummary`,
public keys). `NodeBuilders` no longer dereferences to `OrgService`.
`admit_member`/`revoke_member` return a `BuiltUpdate`, which names the
update org-node holds and carries no part of it. Every production public
method of `OrgIo`, `NodeBuilders`, `NodeView` and `ConnectFailed` returns
only types on a reviewed allowlist. The "no public operation reachable
through org-io … hands out" clause above is now checked over that
allowlist. Classification under the hybrid rule: a clarification (the
requirement's meaning is unchanged; the surface it binds is now closed by
construction); the ID is kept. Verified by
`the_handle_returns_only_allowlisted_public_types` (org-io/tests/absences.rs,
under LLR-3zdw8v).

Owner ruling, 2026-10-06: "neither a user's on-chain private signing key
(sr25519) nor any of their device private signing keys (ed25519) should ever
be exposed." This item states the ruling for org-io; REQ-3pxa8f states how
org-io holds the one private key it does hold. A separate item rather than a
clause of REQ-3pxa8f, because it also binds keys org-io must never hold at
all. The same ruling binds org-node and person for device ed25519 keys; their
existing items are where it is checked, and S2 does not change them.
Verified in the develop phase by a source scan (no getter, no derived `Debug`
or `Display` on a holder, no ed25519 secret type named in org-io's code),
redaction tests on the holder, error-content tests on every error the
custody and parse paths produce, and a test that no type org-io hands the
app (its IPC-facing types) carries key material
(`no_ipc_facing_type_of_the_app_carries_key_material`,
org-io/tests/app_boundary.rs; it was claimed here but missing until review
round 1, 2026-10-08, finding 2).

**REQ-8zuka3**: The software shall read `ODS_ADMIN_SEED` only when built with
its `dev-seed` Cargo feature, which no release build enables; built without
that feature it shall contain no code that reads the variable, shall hold no
signatory key whatever the environment holds, and shall report the chain as
not configured with a message saying that the signing seed is read only by
development builds. (implements: RC-2xufsr)
satisfies: derived

*Reworded 2026-10-07 (reconciliation with the merged code).* The draft said
"when the variable is set it shall … report the chain write as not
configured": a build with no code that reads the variable cannot know whether
it is set, so the report no longer depends on it. "The chain write" became
"the chain" because today's app builds the read and the write together, only
when the seed is configured, and S2 keeps that. *Owner ruling of 2026-10-07*
(the plan's "Still open", item 1): the chain read stays coupled to the
development seed in S2 and is split from the write in S8 (roadmap stage S8,
production custody). Until S8 a release build therefore reads no chain
either; when S8 splits them this clause says "the chain write" again.

The seed in the environment exists for development only (owner, 2026-10-06).
A Cargo feature was chosen over `debug_assertions` because it is the simplest
form to verify: the suite runs with and without the feature, and a source
scan checks that the only read of the variable is behind it. A release build
therefore signs nothing until production custody exists, and, with the read
coupled to the seed (owner ruling of 2026-10-07), reads no chain until S8.

**Production custody, a later stage (not an item here).** In production the
user is prompted to store the signatory key in the OS keychain, or uses a
hardware signing device, and the key is never stored in plaintext by the app
(owner, 2026-10-06). That is not implemented in S2. It is recorded as a stage
of `docs/plans/2026-10-06-org-io-roadmap.md`, not minted here: a requirement
with no test would be MISSING-TEST and block S2's merge, and a problem report
is for a defect and would go stale on planned work. Its requirements are
minted when that stage starts.

**REQ-qnh9pb**: The software shall parse the development seed and the co-signer
list with total functions: the seed is accepted exactly when, after removing
at most one leading `0x`, it is 64 hexadecimal characters, and each co-signer
exactly when, after the same single strip, it is the hex encoding of 32 bytes;
any other input shall be refused with a typed error that names the variable
and the rule it broke and contains no part of the value, and no input shall
make the parse panic. (implements: RC-2xufsr)
satisfies: derived

What this changes. The app's startup parse removed every `0x` prefix, so a
doubled prefix was absorbed rather than reported (the app's problem ledger,
2026-09-14, the startup bullets). The single strip is the rule the app's
other boundary parsers follow. The same seed still yields the same key, so no
working configuration stops working, unless it carries a doubled prefix,
which is now refused by name.

**REQ-6fk4qj**: The software shall provide, through its own public API, every
operation and type the app uses to reach org-node, the chain and the user's
signatory key, so that the app depends on no other workspace unit and on no
chain library.
satisfies: derived
exported: yes

The org-node types the app's commands use are re-exported from one module
marked transitional (accepted recommendation, 2026-10-06); stage S4 narrows
them as the transport and the invitation exchange move. Verified by a test
that reads the app's manifest and finds no `org-node`, `on-chain-client`,
`subxt` or `subxt-signer` dependency.

## The independent trusted root

*Moved 2026-10-07 from `org-node/docs/requirements/2026-09-06-dependency-expectations.md:50`
(ruling A), with the chain read it is about. Its `opened:` date, and so its
age, is unchanged. Restated for org-io: org-node no longer reads the chain.*

**REQ-ysyu9g**: The software shall rely on on-chain-client to return, when
asked for an Organisation's state without naming a block, the Organisation
state recorded at the latest Finalised block, so that the Membership root a
Change set is verified against is never one that a chain reorganisation can
later discard.
expects: on-chain-client
opened: 2026-09-06
satisfies: derived

Why this is an expectation and not org-io's own requirement. org-node's
verify-and-commit path applies a Change set and then compares the recomputed
Membership root against a root obtained from the chain, and that comparison
is only worth anything if the chain read is one the chain will not revoke.
Since S2 that read is org-io's (`read_org_state` over
`OnChainStateReader`, which asks on-chain-client's `get_org_state` with
`at = None`). The read is performed by on-chain-client, which documents the
behaviour in a doc-comment on `get_org_state` ("`at = None` reads at the
latest finalised block") and nowhere else: on-chain-client has no exported
requirement stating it. A doc-comment is not a commitment. This item is what
makes it one, on the provider that performs the read. It was org-node's
expectation from 2026-09-06 until the read moved here.

What org-io owes in return is not an expectation on anyone and is stated as
its own requirement, REQ-tg9zrn above: the state it hands org-node came from
this read and not from the envelope or its author, or is its absence, and a
failed read is reported as an error.
