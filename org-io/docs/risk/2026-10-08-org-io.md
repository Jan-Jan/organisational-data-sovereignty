# org-io: risk analysis for stage S2 (chain IO, key custody, own-admin check)

Change `worktree-org-io-create`. Drafted 2026-10-06 with the requirements in
`org-io/docs/requirements/2026-10-08-org-io.md`. Judged
against this unit's acceptability matrix (`README.md`): S3 is unacceptable at
every probability (ruling D, 2026-10-06), so no S3 residual here is called
acceptable under the matrix.

S2 changes no behaviour. It moves where the chain is read and written and
where the user's signatory key is held. The hazards of the paths that move
stay analysed where they were written (org-node's stale-or-divergent-root
analysis in `org-node/docs/risk/2026-09-09-org-node-hazards.md`, the app's
invitation analysis in `app/docs/risk/2026-10-06-invitation.md`) until the
develop phase moves the items that carry them. This file analyses what S2
makes org-io newly responsible for: holding that key.

## The user's signatory key

Two keys must not be confused here (owner, 2026-10-06). The **Organisation
key pair** is Organisation-wide: the X25519 pair from the key-pair change
(merged as `1f52c36`), held in org-node's Organisation record,
used for encryption and key agreement only, never for signing. It is outside
S2's custody scope and outside this hazard; its disclosure is analysed by
that change in org-node's ledger (`org-node/docs/risk/2026-10-07-org-key-pair.md`). There is **no Organisation-wide signing
key**. On-chain authority comes from each admin user's own sr25519 account,
one signatory of the multisig that controls the Organisation's pure proxy.
That **signatory key** is what org-io holds, and what this section is about.

**HAZ-gaqnc2**: org-io holds this device's user's own sr25519 signatory key,
one signatory of the multisig that controls the pure proxy of every
Organisation that user administers; a path in org-io that exposes the seed or
the key (a getter, a `Debug` rendering, an error message or a log line that
carries it, or a parse error that echoes the configured value) lets whoever
reads that output act as that signatory: because every dispatch is a
threshold-1 multisig call, they can alone submit a Membership root of their
choosing for any of those Organisations, and so admit themselves or keep a
revoked Member in; a Member retaining access they should have lost can expose
an identity in the deployments this project serves. Severity: S3.
Probability: P2.

Severity S3: one signatory's key is enough to rewrite an Organisation's
membership, because the threshold is 1, and the reach is every Organisation
the user administers, not one. Probability P2 before control: the key is
long-lived (the life of the process, and the same seed across restarts),
error values in this code base are routinely formatted into strings that
reach the UI and the log, and a derived `Debug` on a struct holding a secret
has happened here before (a problem report in org-node's ledger, which its
AGENTS.md cites under "Secrets"). One careless `{:?}` is enough.

**RC-2xufsr**: org-io holds the user's signatory seed and key only inside a
type with no operation that returns them and hand-written, redacted `Debug`
and no `Display`; it obtains them only through the development-only
`dev-seed` path, which release builds do not contain, so no release build
holds a seed from the environment; no error, log line, returned value or
IPC-facing type it produces carries the seed, the key or any part of the
configured value, including the errors of the seed and co-signer parse; and
it never receives or outputs a device ed25519 private key: the Persona
store's device seeds stay inside org-node, which offers no public operation
that hands one out. mitigates: HAZ-gaqnc2

*Narrowed 2026-10-08 (review round 1, finding 1), with REQ-v4tfap:* the
"holds" and "opaque sealed bytes" clauses are withdrawn until S4. `OrgIo`
owns the opened `OrgService`, whose store holds the device seeds in memory
until S4 moves them to the OS keychain; that is not exposure. The output
path through the handle's `node()`/`node_mut()` and the `node` re-export is
closed in org-node (crate-private `device_seed`, no production `Serialize`
on `PersonaRecord`/`StoreData`, `OrgEndpoint::inner()` test builds only)
and verified by `org_node_hands_out_no_stored_device_private_key`. The
control covers no private key only; public keys and account IDs may be
exposed (owner clarification, 2026-10-08). Classification: a narrowing;
the ID is kept.

*Clarified 2026-10-08 (review round 2, finding 1), with REQ-v4tfap:* "no
private key" covers the X25519 secrets, the Organisation private key and
the Member seed, as well as the device ed25519 seeds. Their output path is
closed the same way (crate-private `OrgRecord.org_private_key`,
`PersonaRecord.member_seed` and `ProvisionalUpdate.change`; no production
`Serialize` on `OrgRecord` or `ProvisionalUpdate`) and verified by
`org_node_hands_out_no_stored_x25519_secret`. Classification under the
hybrid rule: a clarification; the ID is kept.

*Clarified 2026-10-08 (review round 3, finding 1), with REQ-v4tfap:*
the read surface the control relies on is an allowlist, not a scan for
named secret types. Such a scan missed `node()` → `endpoint()` →
`recv_one()`, which returns a `WireMessage` carrying an Organisation
private key. The handle no longer hands out org-node's service (no
`node()`, no `Deref` on `NodeBuilders`). Its read surface is `NodeView`,
whose methods return public-only summaries. Every production public
method of the handle's types returns only allowlisted types. Classification
under the hybrid rule: a clarification (the control's meaning is unchanged;
its output path is now closed by construction); the ID is kept. Verified by
`the_handle_returns_only_allowlisted_public_types`.

Inherent safety by design (ISO 14971's first rank): the exposure paths are
removed from the type and from release builds, not documented. Implemented
by REQ-v4tfap (no private signing key is ever exposed, owner ruling
2026-10-06), REQ-3pxa8f (custody), REQ-8zuka3 (the seed path is
development-only) and REQ-qnh9pb (the parse's errors carry no part of the
value). Verified in the develop phase by a source scan in the style of
org-node's `absences.rs` (no getter, no derived `Debug` or `Display` on the
holder, the only read of the variable behind the feature, no ed25519 secret
type named in org-io), by `Debug`/`Display` redaction tests on the holder, by
running the suite with and without `dev-seed`, by error-content tests (the
parse tests' abnormal cases and every custody error assert that the text
contains no character run of the input or the key), and by a test that no
IPC-facing type carries key material
(`no_ipc_facing_type_of_the_app_carries_key_material`, org-io/tests/app_boundary.rs,
written at review round 1, 2026-10-08).

Residual: Severity S3, probability P1 after the control. These figures are
kept as assessed. The residual is **not a risk put to acceptance**: the owner
ruled on 2026-10-06 that neither a user's on-chain private signing key
(sr25519) nor any of their device private signing keys (ed25519) may ever be
exposed, and REQ-v4tfap makes that a requirement. Exposure is therefore a
violation of a requirement, controlled by design (RC-2xufsr) and verified by
the tests above. Any route found later by which a key is exposed is a defect,
to be recorded as a problem report and fixed under `resolve-problem`, not an
accepted risk. For context, not as an acceptance argument: release builds
hold no seed until production custody (roadmap stage S8), and the reach of
one exposed key is set by the multisig threshold of 1, which is outside S2.

### The environment

`ODS_ADMIN_SEED` reaches the process through its environment, which child
processes inherit, some platforms expose to other processes, and crash
reporters capture (the app's unminted note "The admin signing key travels in
the process environment", `app/docs/risk/2026-09-14-app-hazards.md`). The
owner ruled on 2026-10-06 that the variable is for development only.
REQ-8zuka3 makes that true of the build: release builds contain no code that
reads it. Production custody is a later stage of
`docs/plans/2026-10-06-org-io-roadmap.md`: the user is prompted to store the
key in the OS keychain, or uses a hardware signing device, and the key is
never stored in plaintext.

## Derived requirements

### REQ-tg9zrn (read the chain, hand org-node the values)

No new hazard. The state org-node judges against comes from the same read as
before (on-chain-client, latest finalised block) through the same parse
(org-node's); only the caller changes. Fails closed: a failed read or a
refused parse reaches org-node as nothing, and the operation that needed it
does not run, which is what org-node's own read did. Reporting a failure as
absence would turn a transient RPC fault into "this Organisation is not on
chain", which org-node answers by refusing, so even that error is
conservative; the requirement forbids it anyway so that S3's
delete-on-verified-revocation never reads a fault as a verdict. The hazard of
verifying against a root a reorganisation can discard stays org-node's
analysis, and the moved finalised-read expectation (REQ-ysyu9g, below)
carries it into this unit.

assesses: REQ-tg9zrn

### REQ-ysyu9g (on-chain-client reads the finalised state)

*Moved 2026-10-07 from `org-node/docs/risk/2026-09-06-dependency-expectations.md:31`
(ruling A), with the expectation it assesses. Restated against org-io's
read; org-node's and org-members' hazards are named by file and description,
never by ID, because only requirements cross a unit boundary.*

REQ-ysyu9g (on-chain-client returns the finalised Organisation state when no
block is named). Hazard impact: **mitigates**, and directly on the decisive
control of org-members' register
(`org-members/docs/risk/2026-09-02-membership-hazards.md`). Its
stale-or-divergent-record hazard and its root-reversion hazard both rest on
the base-matching control, and that register states in as many words that the
root the control compares against must come from a path the attacker does not
control. A best-block read is such a path only until the next reorganisation;
a finalised read is not. Failure behaviour if the expectation is violated: a
revocation is committed against a root the chain later discards, and a
removed Member is believed removed on evidence that no longer exists — the
retained-access pathway, S3. No new hazard is introduced by asking for the
finalised read; its cost is latency, which that register's staleness
discussion already carries. org-node's register
(`org-node/docs/risk/2026-09-09-org-node-hazards.md`) names the hazard this
expectation was written toward, a Change set accepted on its sender's word;
it does not carry `(implements: RC-…)`, deliberately, because an unmet
expectation that implements a control fails the gate on every run, and the
provider's ninety days run to 2026-12-05.

assesses: REQ-ysyu9g

### REQ-f3eu9n (own-admin check)

No hazard impact in S2: nothing acts on the answer. Owner ruling of
2026-10-07: S2 implements the check in org-io with its tests only and does
not wire it into the app, so nothing outside org-io's tests calls it in S2.
A node that is told it is an admin when it is not has every chain write
refused by the chain (the proxy will not dispatch for a non-delegate). A
failed read is an error, not "not an admin", so a fault never demotes a
node silently. When a later stage acts on the answer (S3b-io, its first
caller, then S5's requester check), that stage re-assesses this requirement.

assesses: REQ-f3eu9n

### REQ-qnh9pb (the total seed and co-signer parse)

Assessed with RC-2xufsr above for the content of its errors. Beyond that: no
hazard impact. The parse cannot produce a different key from the one the
configured value names (`x` is outside the hex alphabet, so a stripped prefix
cannot change the body); it refuses what the app's parse absorbed (a doubled
`0x`), which can stop a misconfigured node from starting but cannot let it
sign with a wrong key. Totality (no panic on any input) is fuzzed.

assesses: REQ-qnh9pb

### REQ-6fk4qj (the app reaches everything through org-io)

No hazard impact: it is a dependency rule. Its safety value is that the app,
which renders untrusted input, no longer links the signing library or holds
the user's signatory key (RC-2xufsr's custody), and that S3's workflow has
one owner. The transitional re-exports give the app no path to the
signatory key: org-node never held it. (org-node does hold the Organisation's
X25519 key pair, which signs nothing; the re-exports change nothing about
how it is held.)

assesses: REQ-6fk4qj

### REQ-8zuka3 (the seed path is development-only)

Assessed with RC-2xufsr above, which it helps implement. It adds no hazard:
it removes a route, because a release build contains no code that reads the
seed from the environment. Its cost is availability, not safety: a release
build cannot sign a chain write until production custody exists, and it says
so instead of failing silently. Because S2 keeps the chain read coupled to
the seed, a release build cannot read the chain either, so it verifies and
receives no membership update until S8. That fails closed: with no chain
state, org-node commits nothing and deletes nothing. Owner ruling of
2026-10-07: keep the read coupled in S2 and split it from the write in S8
(roadmap stage S8). This is a ruled availability limit, not an open residual.

assesses: REQ-8zuka3

### REQ-nfr3n2 (submit, then commit and send)

*Moved 2026-10-08 from `app/docs/risk/2026-10-06-invitation.md:78-86`
(ruling A, task T9), with the requirement; the app's `assesses:` line there
keeps its five other requirements. Re-assessed here for the custody that
moved with it.*

No new hazard. The submission is the one the app made, in the same order:
org-node builds, org-io writes through on-chain-client, and only a write
that executed leads to org-node's commit and send; a failed or timed-out
write leaves org-node's record and every peer's untouched and is reported.
What changes is who holds the key that signs the write. The app held the
user's sr25519 signatory key in its chain writer for the life of the
process; org-io now holds it, inside the writer alone, under RC-2xufsr
(no getter, no `Debug` or `Display` that shows it, the seed read only in
development builds), so the app, which renders untrusted input, no longer
links the signing library or holds the key (REQ-6fk4qj). That narrows
HAZ-gaqnc2's exposure rather than adding to it. org-io also reads the chain
the write moved before org-node commits, so the commit is judged against
the chain's state and not the update's own claim; a failed read commits
nothing and is reported. A submission that succeeds and is then not sent
remains org-node's publish-before-persist hazard, as before the move.

assesses: REQ-nfr3n2
