## SDD-6mpmsw — The publish state

`org-io/src/publish.rs` (new): the per-Organisation state org-io keeps
between calls — the chain write whose outcome is unknown, the verification
status of each held Organisation — and the sequences over it, reached as
`OrgIo` methods (`settle_unknown`, `reconcile`, `reconcile_held`,
`verification`) and from `submit::submit_commit_send`. Its public report
types (`Settled`, `Reconciliation`, `Verification`) hold public data only and
join `HANDLE_RETURN_ALLOWLIST`. *Amended in place 2026-10-13 (owner ruling of
that day, background discard): `discard_update`, `discard_genesis` and
`DiscardRefused` leave the public surface; the discard is the settle's own
(LLR-t98pk9) and the commit's (LLR-fptp57, LLR-36zp69).* The state is held in memory, in one field of
`OrgIo` (`PublishState`), so stage S4's move of the handle behind its own
lock is one field (plan §4). The chain's two new seams: `ChainWriter` gains
`write_window()` and `update(.., window)`, and `StateReader` gains
`finalised_block()`; the production implementations are the chain
connection item's (SDD-z85ux9).

**SDD-6mpmsw**: the publish state: settling a chain write whose outcome is
unknown, reconciling each held Organisation with the chain and keeping its
verification status, and discarding provisional updates, each over org-io's
chain read and org-node's operations, deleting nothing outside org-node's
verified paths.
traces: REQ-by9k5q, REQ-77rh5a, REQ-dqbg9p, REQ-cz753a

*Clarified 2026-10-14 (master's S3b-io part 1 merged into S4,
`worktree-org-io-transport`; hybrid rule, a clarification):* on S4's
structure `PublishState` sits behind its own `tokio::sync::Mutex` in
`OrgIo`, taken after the node's lock by every method that takes both; the
publish methods take `&self` and hold the node's lock for their whole
sequence, chain reads included, as S4's submission does (S4 LLR-9arvqj's
note). org-node saves nothing: each of its operations here returns a store
change that org-io writes through its store files before reporting, and a
write that fails reloads the Persona from its file (S4, task T9). A late
commit is sent through S4's fan-out (`send_committed`).

**LLR-2yjuaj**: `submit_commit_send`, after its three pre-write refusals and
before the write, calls `ChainWriter::write_window()` once and passes the
window to `ChainWriter::update`; when `write_window` fails it writes nothing
and returns an error saying no write was made. When the bounded write times
out (`WriteNotDone::TimedOut`), it records for the Organisation an unknown
write holding the `BuiltUpdate`, the recipient, the peer address and the
window's `last_valid_block()`, and returns S2's unknown-outcome report; on
any other result it records nothing.
satisfies: REQ-by9k5q

*Clarified in place 2026-10-13 (unmerged draft; task T14):* "an error saying
no write was made" is S2's failed-write report, "chain write failed; nothing
committed or sent: …", with the window read's failure as its cause; the
prefix is kept so the app sees one form for every refusal before a write
executed.

*Amended in place 2026-10-13 (unmerged draft; review round 1, finding-3):*
the unknown write also holds the epoch the write expected (the record's
epoch passed to `ChainWriter::update`), which LLR-t98pk9 settles against.

*Clarified 2026-10-14 (S3b-io part 1 merged into S4; hybrid rule):* since
S4's task T12 a submission names no recipient — its commit is sent to every
recipient org-node built a body for — so the unknown write holds no
recipient; it holds the `BuiltUpdate`, the peer address the submission was
given (org-io's `PeerAddr`, the one address a Loopback send dials), the
`last_valid_block()` and the expected epoch.

**LLR-t98pk9**: `OrgIo::settle_unknown(rng, org_id) -> Settled`, for an
Organisation with an unknown write, calls `StateReader::finalised_block()`
then `StateReader::read_state(org_id)` once each, in that order, and returns:
`Committed { org_id, epoch, sent }` when the state holds the update's
Membership root and Organisation public key — after org-node's `reconcile`
with that state commits it, sending the committed update with `send_update`
to the recorded recipient (`sent` is `Ok(())` or the send's error; a failed
send does not unwind the commit); `Reconciled(Reconciliation)` when the
state is at a newer epoch with another root (LLR-k5pzsz's result for that
state); `NotExecuted { org_id }` when the state is at the record's epoch
and the finalised block read is greater than the recorded
`last_valid_block`; and `StillUnknown { org_id, reason }` when the state is
still at the record's epoch within the window, when either read fails, or
when the parse refuses the state. Every result but `StillUnknown` clears the
unknown write. An Organisation with none returns `Settled::NoUnknownWrite`
with no read.
satisfies: REQ-by9k5q

*Amended in place 2026-10-13 (unmerged draft; task T14, design gaps the
implementation found):* two cases the text left open are now stated. A
`read_state` that finds no state (`Ok(None)`, reported as org-node's
`OrgNotOnChain`), or a state at an epoch older than the record's, is
`StillUnknown` with that reason, and keeps the unknown write. A record that
org-io no longer holds when the state shows another root goes through
org-node's `reconcile`, whose `OrgNotHeld` refusal is reported as
`Reconciled(Refused { .. })` and clears the unknown write. Tests for the two
added cases are written in task T15 (`publish_path.rs`:
`a_settle_that_finds_no_state_or_an_older_state_stays_unknown`,
`a_settle_whose_record_is_no_longer_held_is_refused`).

*Amended in place 2026-10-13 (unmerged draft; owner ruling of that day,
background discard):* on `NotExecuted` the settle also discards the update
itself, before returning, through org-node's `discard_provisional` (its
Organisation, resulting root and Organisation public key), removing the
Organisation private key it holds; when that discard cannot save the store
it returns `StillUnknown` with the reason and keeps the unknown write, so
it is tried again. It never discards before `NotExecuted` (owner ruling D3).

*Note 2026-10-13 (owner ruling):* a failed save of that discard leaves the
update removed from org-node's memory but its Organisation private key on
disk until the next successful save (org-node's `discard_provisional`
removes before it saves). The retry finds nothing left to discard and
returns `NotExecuted`. This memory-ahead-of-disk behaviour is booked under
org-node's save-after-mutate problem report, widened the same day, for S4 to
fix; it is not fixed here.

*Amended in place 2026-10-13 (unmerged draft; review round 1, findings 1
and 3):* two cases the text left open are now stated. (a) When the state
holds the update's root and key but org-node's `reconcile` finds the record
already in step (the update was committed before this settle), the result
is `Reconciled(InStep { .. })`, the unknown write is cleared, and it counts
as settled: `submit_commit_send` goes on to its own write (LLR-nqvbb6).
Nothing is sent then: org-node offers no send of an update committed
earlier, and every commit of the update org-io drives already sent it or
cleared the write (LLR-k5pzsz). (b) When the record's epoch is already past
the epoch the write expected (LLR-2yjuaj) — a received update or a
reconcile moved it — the contract's epoch check can never pass the write:
the settle reads nothing and returns `NotExecuted { org_id }` at once,
discarding the update as above (org-node's `NoProvisionalUpdate`, when the
commit that moved the record already dropped it, counts as discarded). The
"calls `finalised_block()` then `read_state` once each" clause holds for
every other case.

*Note 2026-10-13 (unmerged draft; review round 2, finding-1):* the earlier
amendment's "It never discards before `NotExecuted` (owner ruling D3)" stays
true, and case (b) is a `NotExecuted` reached with no read inside the window
(REQ-by9k5q's dated note of the same day). D3 forbids discarding an update
whose write may still execute; in case (b) the write cannot execute (the
contract's epoch check), and the commit that moved the record already
dropped the update (org-node's `discard_orphans`), so the discard returns
`NoProvisionalUpdate` and does nothing.

*Clarified 2026-10-14 (S3b-io part 1 merged into S4; hybrid rule):* on S4's
structure "sending the committed update with `send_update` to the recorded
recipient" is S4's fan-out: every body org-node's commit built goes to its
recipient from the sending Persona's endpoint, at the recorded peer address
in Loopback mode (S4 LLR-znhmh2, LLR-r9sh6k), and `sent` is `Ok(())` when
every send succeeded, else an `Err` naming each Device whose send failed.
org-node's `reconcile` and `discard_provisional` save nothing; org-io writes
the store change each returns. The "cannot save the store" case is a store
write that failed: the Persona is reloaded from its file, so the update is
held in memory again as on disk, and the settle returns `StillUnknown` and
keeps the write — the note above on memory ahead of disk no longer applies
(org-node's save-after-mutate report, resolved by S4's tasks T3 and T9). An
executed write whose commit is not stored is likewise `StillUnknown`, the
write kept, to be settled again.

*Amended in place 2026-10-15 (S4 review round 2, A3; PR-9q5ems):* case (b)
is narrowed to what the record shows. It applies when the record is at the
epoch after the one the write expected and does not hold the update's
Membership root and Organisation public key: another update took the epoch
the write would have produced, so the write did not execute. A record
further on, or one holding the update, does not show which update took that
epoch (a commit the settle did not drive can have committed this write's
update and later ones), so the settle reads as in every other case, and the
"still at the record's epoch" cases apply only while the record and the
chain are both at the epoch the write expected. A chain at a newer epoch
with another root is then `Reconciled(..)`, the main clause's result, never
`NotExecuted`: the settle reports no outcome the chain's evidence does not
show.

Test: `org-io/tests/publish_path.rs`.

**LLR-nqvbb6**: `submit_commit_send` for an Organisation with an unknown write

the update was discarded, and that it must be rebuilt and submitted again.

**LLR-k5pzsz**: `OrgIo::reconcile(rng, org_id) -> Reconciliation` calls
`StateReader::read_state(org_id)` once and hands the result to org-node's
`reconcile`, and maps its result: `InStep { org_id, epoch }`;
`Committed { org_id, epoch, recipients }`, where `recipients` are the
DevicePublicKeys the committed update is for (every Device the committed
record lists other than this node's own, then each Device its notices name);
`Behind { org_id, chain_epoch }`; `Removed { org_id }`, keeping the
acknowledgements org-node signed in org-io's memory for part 2 and never
returning them; and `Refused { org_id, reason }` for any refusal of
org-node's. `OrgIo::reconcile_held(rng)` does this for every Organisation
the store holds, in store order. Neither sends anything.
satisfies: REQ-77rh5a

*Amended in place 2026-10-13 (unmerged draft; review round 1, finding-1):*
"Neither sends anything" gains one exception, which REQ-by9k5q's "whenever
the app asks" needs (the app asks through `reconcile_held`). When the
Organisation has an unknown write (LLR-2yjuaj) and the state read holds its
update's Membership root and Organisation public key, the reconcile clears
the unknown write whatever org-node returns, and when org-node's
`reconcile` commits that update it sends the committed update with
`send_update` to the Device the submission named, at its recorded peer
address. The send's failure does not unwind the commit and does not change
the result (`Committed { .. }`, whose `recipients` include that Device). A
state that does not hold the update leaves the unknown write to
LLR-t98pk9's settle. This item now also serves REQ-by9k5q.
satisfies: REQ-by9k5q

*Note 2026-10-13 (review round 2, finding-3; owner ruling of that day):*
when org-node's `reconcile` commits that update in memory but fails to save
the store, it returns an error. The unknown write is still cleared, and the
send to the recorded Device is lost. A later reconcile finds the record in
step and has nothing to send. Keeping the write would not help: the next
settle would find the record past the write's expected epoch and report the
executed write as not executed. The cause is org-node's: `reconcile` puts the
committed store into memory before saving. It is booked in org-node's
problems ledger, `org-node/docs/problems/2026-10-13-publish.md` (named here
by description: org-node exports no item), for S4 to fix with the
memory-ahead-of-disk class. "Whatever org-node returns" stands.

*Clarified 2026-10-14 (S3b-io part 1 merged into S4; hybrid rule):* on S4's
structure org-node's `reconcile` changes a copy and returns its store
change, saving nothing; org-io writes it. When that write fails, the
Persona is reloaded from its file, so the commit is undone in memory too,
the result is `Refused` with the store failure as its reason, and the
unknown write is kept rather than cleared: the next reconcile or settle
commits the update again and sends it. The note above (round 2, finding-3)
describes S2's org-node; "whatever org-node returns" now excepts a store
write that failed. The send is S4's fan-out to every recipient, at the
recorded peer address, not `send_update` to one Device. `recipients` are
the recipients of the bodies org-node's commit built (S4, task T5), the
same Devices in the same order.

## The own-admin rule, superseded (task T16a; owner rulings D4, D5)

**LLR-2hkqv2**: `admin_status(controller, set: &SignatorySetView) -> AdminStatus`
returns `Admin` exactly when `set.original_account` is `Some` and
`set.definitions` holds a definition whose delegate is `controller`, whose
proxy type is the runtime's `Any` (the index the read resolved from
metadata, `set.any_proxy_type`) and whose delay is 0;
`DelegateCannotDispatch` when the account is mapped and some definition
names `controller` but none is `(controller, Any, 0)`; and `NotAdmin`
otherwise. `OrgIo::is_own_admin` obtains `set` from one signatory-set read
(on-chain-client's pinned read); a failed read is
`OwnAdminError::Read`, never `NotAdmin`.
satisfies: REQ-ntkjk6
