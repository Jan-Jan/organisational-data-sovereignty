## Derived requirements assessment

### The acknowledged record (REQ-h7y5ur, REQ-f8pu8a)

HAZ-7ubhwz (an acknowledgement the named Device did not produce is accepted
and recorded; the Organisation believes a revoked Device cleared that did
not): the record keeps only what RC-eydn8t's check already accepted — the
sender authenticated as the named Device, the Device absent from the current
record, the signature verified under the acknowledgement's domain — and adds
a further condition, that this Member holds the Device as revoked. Keeping
it therefore adds no way for a forged acknowledgement to be recorded. It is
never shared (ruling 5), so no peer merges it, and HAZ-7ubhwz's "treated as
revoked by every peer that merges the list" has no path through it. What the
record says is RC-eydn8t's "not evidence of erasure": the Device signed that
it acted on its removal. The app's view of it states that (app
`2026-11-02-publish-2.md`, its own hazard), since there the risk is a
misreading by the Admin, not a wrong record.

Resource exhaustion (HAZ-cuj9gn's flooding case, by analogy): the record is
outside LLR-m76r4k's 1 MiB bound, so its growth must be bounded by design.
It holds at most one entry per Device held as revoked, and `revoked_devices`
grows only when this Member adopts an epoch verified against the chain.
Neither a stolen revoked Device nor a key never listed can grow it by signing
more acknowledgements: a second acknowledgement from a Device already kept,
and one from a Device not held as revoked, are accepted and not kept. The
bound is the Organisation's own removal history.

REQ-f8pu8a returns public values only (MemberIds, DevicePublicKeys, signed
acknowledgements the Device sent in the clear) and changes nothing. No
hazard impact.

assesses: REQ-h7y5ur, REQ-f8pu8a

### The delivering Device first (REQ-32cp7f)

HAZ-h6b34a (the state a revoked Device keeps to deliver its acknowledgement
outlives the deletion of everything else on a lost or stolen Device):
REQ-32cp7f changes which Devices are recipients, not how many (REQ-6tepxq,
unchanged) nor how long the state is kept (org-io's deletion requirement, 7 days). The
delivering Device is a candidate already (the sender rule), so the set of
DevicePublicKeys and addresses a thief can learn is a subset of the record
before the removal, as before. The rating is unchanged.

Its benefit side: the delivering Device is the one that wrote or answered
the removal — in the single-Admin stage the Admin's own Device for a pushed
epoch or notice — so the acknowledgement reaches the Admin, whose view
(REQ-f8pu8a) is the one that shows it. Under the old order the Admin's
Device was chosen only when its key bytes sorted first.

Keeping the notice's sender (`KeptNotice.from`) stores a DevicePublicKey the
record already lists; dropped with every kept notice at the next adoption.
No exposure.

Residual: the delivering Device may have no address in the removed Device's
address book (a notice answered by a Member this Device reached through
discovery; an epoch sent by an Admin Device other than the one that issued
this Device's Invite). The acknowledgement kept for it is then reachable
only as org-io's T16c4 requirement allows (*owner ruling Q1 (c) of
2026-11-03*: a dial by key in Networked mode); at
worst one of up to three acknowledgements is not delivered, which is
HAZ-h6b34a's benefit side, not a wrong deletion and not a disclosure.

assesses: REQ-32cp7f

## The held-as-revoked residual (LLR-bgj2ff; plan task T18)

A Device admitted and removed between two epochs this Member adopted is
never held as revoked by it. That happens when the Member jumps epochs
through an organisation answer (an answer carries no Change set, so the
adoption replaces the record with one that never listed that Device), or
adopts a later epoch whose base already lacks it. Consequences:

- that Member refuses the Device's organisation request (`SenderNotListed`,
  LLR-283x6f), so the Device does not learn of its removal from that Member;
  it learns from any Member that holds it as revoked, or from the notice the
  send step pushed (REQ-p4hwuv);
- that Member accepts the Device's acknowledgement (REQ-b462sh) but keeps
  nothing (REQ-h7y5ur), so its acknowledged record does not show it.

Effect on HAZ-vxabf9 and HAZ-h6b34a: a removed Device that learns of its
removal later keeps its data longer. It already holds no key of any epoch
after its removal (each epoch rotates the Organisation key pair), so the
exposure is the data it held before, which it held anyway until it learns.
In the single-Admin stage the Admin writes, and so adopts, every epoch in
order, so the Admin holds every removed Device as revoked and its view is
complete; the residual concerns other Members only. Rating
unchanged; acceptable until roadmap stage S5, whose shared revoked-device
list closes it (*owner ruling Q5 of 2026-11-03*, accepting the analyst's
recommendation as drafted). Recorded on
LLR-bgj2ff by a dated note of 2026-11-03.
