**PR-6f3qku**: `cargo clippy -p org-node --features app,test-support
--all-targets -- -D warnings` fails on four existing test targets —
`fuzz_verify_against_chain`, `key_custody`, `transport_handshake` and
`value_types` — so the crate's tests are not lint-clean under clippy 1.99,
and a per-task clippy run over all targets cannot be used as a gate.
affects: LLR-hs7g6j, LLR-98ufry, LLR-k2y6nn, LLR-2smrvx, LLR-7cgg8a
opened: 2026-10-07
status: open

Measured 2026-10-07 on the S3a tree (clippy 0.1.99, b940084d7e 2026-09-28,
agent sandbox, `--keep-going` so every target is reported):

- `fuzz_verify_against_chain` (`tests/fuzz_verify_against_chain/fuzz_target.rs`):
  22 errors — `unwrap_used` and `expect_used` throughout, one
  `explicit_auto_deref` at `:127`.
- `key_custody` (`tests/key_custody.rs`): 4 errors — `needless_maybe_sized`
  at `:141` and `assertions_on_constants` at `:156`–`:158` (the `CloneProbe`
  assertions of `an_x25519_key_pair_cannot_be_cloned`, which are constant by
  design).
- `transport_handshake` (`tests/transport_handshake.rs`): 2 errors — `panic`
  at `:370` and `:433`, both lines from `05f6f04` (before S3).
- `value_types` (`tests/value_types.rs`): 1 error — `panic` at `:173`.

Every other target, the library and every target S3 added
(`commit_paths`, `revocation`, `reconcile`, `commit_workflow_errors`) is
clean. The four red targets were already red before S3 began; S3 touched
only `transport_handshake`, in lines clippy does not flag. Newer test files
open with `#![allow(clippy::unwrap_used, clippy::expect_used, clippy::panic)]`;
three of these four allow only `unwrap_used` and `expect_used`, and the fuzz
target allows none, while the workspace lints deny all three in every
target. `verify_commands` runs `cargo test`, not clippy, so no gate
has caught it.

Why it matters: under class C the robustness tests are evidence, and a lint
gate that cannot be run over them leaves new test code unlinted; S3's plan
had to narrow its per-task clippy to the targets each task touched (T0).

The fix, in outline: give the four targets the same test-file allow header
with `clippy::panic` (and `#[allow(clippy::assertions_on_constants)]` on
the probe test, the redundant `?Sized` bound dropped), then add `cargo clippy … --all-targets -- -D warnings`
to `verify_commands` so it stays clean.

**PR-eqs4fs**: a founding Persona's `member_id` stays `None` after
`commit_genesis`, so when the founder's node is removed — by committing its
own removal, by a revocation notice it accepts, or by a reconcile —
`sign_acknowledgements` skips that Persona and the node forgets the
Organisation having signed no acknowledgement for it.
affects: REQ-y99c9w, LLR-hby4jr, LLR-b27jr6
opened: 2026-10-07
status: resolved
resolution: fixed 2026-10-07 (change `worktree-org-io-commit-workflow`, task
s3t12b): `commit_genesis` binds the founding Persona with the MemberId of
the genesis leaf that lists its Device, as the first admission does on the
receive path, so no bound Persona lacks one and `sign_acknowledgements`
signs for the founder; LLR-hby4jr amended in place to drop the "whose
`member_id` is set" narrowing. No fallback for a stored founder without a
MemberId: stores written before S3 do not load (plan decision 12). Test
`a_founder_that_commits_its_own_removal_signs_its_acknowledgement`
(`org-node/tests/commit_paths.rs`): red before (no acknowledgement), green
after; `commit_genesis_creates_the_record_once_the_chain_carries_the_root`,
which pinned `member_id: None`, now asserts the genesis MemberId.

Where: `create_persona` in `org-node/src/service.rs` creates every Persona
with `member_id: None`; `commit_genesis` binds the founder through
`update_persona_status`, which sets `status` and `org_id` and never
`member_id`, although `create_organisation` drew the founder's MemberId
(`fresh_member_id`) for the genesis leaf. Only the receive path's first
admission sets `member_id` (the "Mark persona as Active + set member_id"
block in `receive_and_verify`). `revocation::sign_acknowledgements` then
filters `let Some(member_id) = persona.member_id else { continue };` — a
bound Persona without one is skipped silently, with no refusal. All three
removal paths (`accept`, `commit_step` through `removal_step`, `reconcile`)
sign through it.

Confirmed 2026-10-07 by a temporary probe test, run once and not kept:
founder A and member B (`admit_b_directly`); A's Persona reads
`member_id: None` after `commit_genesis`; A revokes its own MemberId, the
chain takes the update and A's `commit_update` succeeds with
`outcome.acknowledgements.len() == 0`, the record gone and the founder's
Persona deleted. A Persona admitted on the receive path signs one, as
`a_node_that_commits_its_own_removal_forgets_the_organisation`
(`org-node/tests/commit_paths.rs`) shows for B.

Why it is a defect: REQ-y99c9w requires an acknowledgement "for each Persona
bound to that Organisation". LLR-hby4jr narrows that to Personas "whose
`member_id` is set", so the code meets its LLR while the LLR does not meet
its REQ. The founder is the Organisation's first administrator; a lost or
stolen founder Device that is revoked and clears itself can never report
that it did (HAZ-7ubhwz's acknowledgement is what tells the Organisation a
cleared Device from a silent one), and the deletion still happens, so the
failure is silent. No data is retained and no key leaks.

The fix, in outline: set the founder's `member_id` in `commit_genesis` from
the genesis leaf whose Device is the Persona's, and either derive the
MemberId in `sign_acknowledgements` from the verified record by the
Persona's Device, or refuse rather than skip a bound Persona with none;
amend LLR-hby4jr to drop the "whose `member_id` is set" narrowing. The
reproducing test is the founder's self-removal above, asserting one
acknowledgement naming the founder's MemberId.

with dated amendment notes quoting the old text, instead of superseding them
(a new ID with a `supersedes:`/`superseded-by:` pair and dual-ID `verifies:`

opened: 2026-10-07

Recorded 2026-10-07 from the independent review of change
`worktree-org-io-commit-workflow` (round 1, finding-9), for the owner to rule
on the practice. Reworded in place with dated notes, none with a
supersession pair: REQ-ztdza4 (meaning reversed: from "commit whoever sent
it" to "commit only from a Device the current record lists", owner ruling R1,
decision 16 of `docs/plans/2026-10-06-org-io-commit-workflow.md`),
REQ-uxv2x2, REQ-uv3v5w, REQ-3dsweu; RC-wqgm2p, RC-b6mydy; LLR-js9dsu,
LLR-pt32fx, LLR-38e2kn, LLR-6ymd6d, LLR-8hdu9x, LLR-hby4jr, LLR-5azhry.

What holds: each note quotes the text it replaces and names the ruling or
task behind it, and the plan rules these items "amended in place", so the
tree stays traceable and check-trace passes. What does not: a test that
`verifies:` one of these IDs no longer says which wording it was written
against, and a reader of REQ-ztdza4's ID alone cannot tell which of two
opposite rules is meant without reading its notes; the checklist's rule
exists to prevent exactly that, most of all for a reversed meaning.

The decision for the owner: either confirm amendment in place with dated,
quoting notes as this project's practice (and have the checklist say so,
with a limit such as "a reversal of meaning is always superseded"), or
supersede the items above — at least REQ-ztdza4 — in a follow-up change,
with new IDs, `supersedes:`/`superseded-by:` pairs and the tests
re-annotated.

**PR-m9betm**: `revocation::sign_acknowledgements` still skips, silently, a
Persona bound to the Organisation whose `member_id` is `None` (`let
Some(member_id) = persona.member_id else { continue };`,
`org-node/src/revocation.rs`), so a removal through `accept`, `commit_step`
or `reconcile` would go ahead with no acknowledgement for that Persona and
no refusal.
affects: LLR-hby4jr, REQ-y99c9w
opened: 2026-10-07
status: open

Recorded 2026-10-07 from the independent review of change
`worktree-org-io-commit-workflow` (round 2, finding-2); not fixed in this
change. The state is unreachable today: every path that binds a Persona
(`commit_genesis` since PR-eqs4fs, and a first admission on
`receive_and_verify`) sets `member_id` with `org_id`, and stores written
before S3 do not load (plan decision 12). Still, the skip is behaviour no
requirement states: REQ-y99c9w and LLR-hby4jr (as amended for PR-eqs4fs)
require one acknowledgement per bound Persona, and PR-eqs4fs's own fix
outline proposed to "refuse rather than skip a bound Persona with none".

The fix, in outline: refuse with a new typed `OrgNodeError` variant naming
the Organisation instead of `continue`, before any acknowledgement is
returned and so before anything is forgotten; amend LLR-n67aw8 (the new
variant) and LLR-hby4jr (the refusal); test it with a store holding a bound
Persona whose `member_id` is `None`, on `sign_acknowledgements` and through
`accept`, asserting the refusal, no acknowledgement and the store unchanged.
