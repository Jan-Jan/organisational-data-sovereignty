# org-node without IO: the sealed store, one receive path, outgoing bytes and Invites (stage S4)

Change `worktree-org-io-transport`, stage S4. Drafted 2026-10-06, before any
code. The key-pair change those rulings waited for merged on 2026-10-07
(`1f52c36`); S4's code starts once S2 has merged (plan, task T0). Until then
each requirement below is reported MISSING-TEST, which is the truth.

By the owner's ruling B (2026-10-06), org-node meets org-io by values in and
values out: it takes the values it judges against and returns the values to
be written or sent, including the sealed store bytes. It has no IO traits, no
async, no file and no endpoint. S2 moves the chain read out
(`docs/adr/2026-10-06-org-io-unit.md`); S4 moves the rest: the store file,
the transport and the invitation exchange's running. These requirements
state the values org-node provides in their place. Each is exported, because
org-io depends on org-node and relies on it for exactly these values; each
answers one of org-io's stated expectations, named in its `satisfies:` line
(org-io's ledger file `org-io/docs/requirements/2026-10-06-transport.md`).

## Requirements

**REQ-x3jrh8**: The software shall open a Persona store only from sealed
bytes and the Persona's transient device secret given to it as values, or
start a new store only when it creates that Persona, one store per Persona,
and shall return, from every operation that changes the store, the
complete sealed store as bytes that the caller must handle (ignoring them is
refused at compile time under the workspace lints); it shall read and write
no file.
satisfies: REQ-x6kdse
exported: yes

What this changes: `PersonaStore` loses its path, `open` becomes `unseal`
(today's `open` without `exists` and `fs::read`), `save` becomes `seal`
(today's `save` without `fs::write`), and every operation that today ends in
`store.save(rng)` returns the sealed store beside its result. The AEAD is
unchanged; its key is no longer passphrase-derived but derived from the
device secret (REQ-qthum6). REQ-hzm4kt's ciphertext-only rule now governs the
bytes given out rather than the file written. Outstanding invite identifiers join the
sealed data (an earlier form of REQ-ky5tyd), so the golden plaintext is re-pinned.

*Clarified 2026-10-14 (review round 1 of S4, finding-7), a narrowing of the
wording to what the tree enforces, not of the intent:* "ignoring them is
refused at compile time under the workspace lints" means a *discarded
statement*: a call whose returned write (`StoreWrite`, `#[must_use]`) is
dropped as an expression statement does not compile, because the workspace
sets `unused_must_use = "deny"`. An explicit `let _ = …` binding of the
returned value compiles: the lint does not see it, so dropping the bytes that
way is a review matter, not a compile error.

*An endpoint-secret requirement drafted here was dropped before first merge
(owner ruling, 2026-10-06): org-io builds iroh's secret key from the
keychain-held seed itself, and org-node has no iroh or `iroh-base`
dependency and no endpoint-secret type.*

**REQ-26mjqa**: The software shall accept a Persona's device secret only as
a transient, opaque value that cannot be cloned, renders a fixed marker in
`Debug`, has no `Display`, cannot be serialised and offers no operation
returning its bytes except one scoped write that lends them to a single
caller-supplied keychain call; shall consume that value within the one
operation it is given to (deriving the store key, or signing) and overwrite it with zeros when that operation ends; and
shall persist neither the device private seed nor anything derived from it,
the store key included; and shall never call the OS keychain, which only
org-io touches.
satisfies: REQ-v6r2gd
exported: yes

Owner rulings of 2026-10-06: the device ed25519 private seed lives only in
the OS keychain, which org-io reads; org-node keeps only the Device public
key and uses the private seed per operation. Creating a Persona draws the
device seed as today (the item LLR-d4gpxm and LLR-6acxu9 replaced) but returns it as this value, for org-io to
write to the keychain, instead of keeping it. The signing the S3 change adds
(the revoked device's signed acknowledgement) takes the seed the same way, as
a transient value; that change's signing requirement is amended to say so
(plan §12).

**REQ-qthum6**: The software shall seal and unseal a Persona's store only
under a key derived from that Persona's device secret by HKDF-SHA-256 with a
fixed, versioned ODS store-key label as its info input, so that the store key
is never the signing key and never equal to any other key derived from the
same seed; shall keep in the sealed store the Persona's Device public key and
never its device private seed; and shall offer no passphrase-derived store
key.
satisfies: REQ-qza96g
exported: yes

What this changes: Argon2 and the fixed application salt go (the residual
REQ-hzm4kt's control carried), and so does the passphrase: the app stops
prompting for one (its passphrase requirement and control are amended in
develop). A Persona's other secrets, its X25519 member seed and each
Organisation's X25519 private key, stay in the sealed store under the new
key. The salt input of the derivation is the Persona's Device public key, so
two Personas' store keys differ even in principle; the label is
domain separation, and a new version of it is a new key. One sealed store
per Persona, each keyed by its own Persona's device secret (owner ruling,
2026-10-06).

**REQ-uy7kfq**: The software shall let at most one of a node's Personas
belong to, or await admission to, any one Organisation: it shall refuse,
with a typed error and changing nothing, to record an expected admission
for an Organisation that another Persona held by the node is bound to or
already expects admission to.
satisfies: derived

REQ-uy7kfq follows the owner's ruling of 2026-10-13 (S4, raised by task
T3): an individual is a member of an Organisation only once. It is
enforceable only within one node, and that is accepted as enough. It is the
other direction of REQ-yp75u9 (a Persona belongs to at most one
Organisation). With one Persona per sealed store (an earlier form of LLR-f9x3vf), two Personas
in one Organisation would each hold a copy of its record while every
received update commits into one store only, so the other copy would go
stale. Refusing the second expectation makes that state unreachable. A
first admission is committed only for an Organisation the node expects
(an earlier form of REQ-eqt23j), so the refusal sits where the expectation is recorded. Today
that is `expect_admission`, and from task T6 the reply build.
