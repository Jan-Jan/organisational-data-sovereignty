# Design — values in, values out: org-node reads no chain

Low-level requirement for change `worktree-org-io-create` (stage S2 of
`docs/plans/2026-10-06-org-io-roadmap.md`), owner ruling B of 2026-10-06:
org-node meets org-io by values in, values out. org-io reads the chain and
hands org-node each Organisation state as a value; org-node names no chain
library and holds no chain seam. The item below sits under SDD-ueh4tm (the
boundary between the user stories and the chain, in
`2026-10-03-decomposition.md`, amended 2026-10-08 to say that boundary is now
the state value each chain-judging operation takes) and refines REQ-bvh8v6,
the requirement SDD-ueh4tm and LLR-8m99q2 already serve: the Organisation's
state comes from a path the sender does not control. It is that item's only
new low-level requirement in this change.

**LLR-mn5c2q**: org-node's source names no `on_chain_client::` or
`subxt::` path, and no `ChainOps`, `ChainReader`, `read_state`,
`OnChainReader`, `OrgStateCache` or `connect_chain_client`; its manifest
has no `chain` feature and no `subxt`, `on-chain-client`, `async-trait` or
`hex` dependency; every operation that judges against the chain
(`commit_genesis`, `commit_update`, `reconcile`, `apply_receive`,
`apply_self_delete`, `verify_envelope_against_chain`) takes the
Organisation's state as an `Option<OrgState>` argument and is
synchronous.
satisfies: REQ-bvh8v6
supersedes: LLR-65py3d

*Supersession (2026-10-08, owner ruling on PR-zf924s, hybrid).* LLR-65py3d
said `ChainOps` presents reading an Organisation's state as an asynchronous
operation on a trait object, so a substitute may be injected. Ruling B
removes the trait and the read: that is a change of meaning, so this item
supersedes it rather than amending it in place. What LLR-65py3d also said —
org-node presents no operation that writes to the chain — still holds, and
the test that carries it (`absences.rs`'s
`the_service_presents_no_chain_write`) is unchanged. The test of this item
(`org_node_names_no_chain_library_and_reads_no_chain`) names both IDs.

*Note 2026-10-08 (robustness, N/A):* `org_node_names_no_chain_library_and_reads_no_chain` is a source and manifest scan. The property is an absence and takes no input, so it has no abnormal-input case; it was watched red with the preflight bin still naming `on_chain_client::` (S2 T6).

## Added 2026-10-08: a by-reference query of the held updates

*Added 2026-10-08 (S2 review round 4, finding 2).* org-io's pre-write guard
asked whether org-node holds the update it is about to write by taking
`provisional_updates(org_id)`, which clones every held `ProvisionalUpdate`
with the Organisation private key inside its `ProvisionalChange`, to compare
four public fields. `OrgPrivateKey` is never wiped, so each copy is an
unwiped secret, against the ruling that keys only move. This item gives the
guard a query that copies nothing; it is the second new low-level
requirement of this file, beside LLR-mn5c2q.

**LLR-gwk4nk**: `OrgService::holds_provisional(org_id, base_root,
resulting_root, org_pub_key) -> bool` answers whether the store holds a
provisional update whose `org_id` is `org_id`, whose base root is
`base_root`, and whose resulting root and Organisation public key are those
given; it compares the stored updates by reference, copies no
`ProvisionalUpdate` and no Organisation private key, and changes nothing in
the store.
satisfies: REQ-xs4ab8, REQ-ech45n

*Note 2026-10-08 (test):* `commit_paths.rs`'s
`holds_provisional_matches_all_four_public_fields_and_writes_nothing` carries
the normal case and the abnormal ones: another Organisation, base root,
resulting root or public key each answers false, and the store's bytes are
unchanged. It was watched red with the method missing, and again with the
base-root comparison removed ("another base root").
