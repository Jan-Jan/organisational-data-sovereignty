Software items and low-level requirements for change
`worktree-org-io-transport`, stage S4 of
`docs/plans/2026-10-06-org-io-roadmap.md`. They refine org-node's S4
requirements (`org-node/docs/requirements/2026-10-06-sans-io.md`:
REQ-x3jrh8, REQ-26mjqa, REQ-qthum6, REQ-2ugh2f, REQ-6ehufy, REQ-58tzex),
each of which answers one of org-io's expectations. Plan:
`docs/plans/2026-10-06-org-io-transport.md` ("## Tasks"). Drafted 2026-10-07,
before any code; every item is class C, the unit's class.

*Reviewed 2026-10-07 against the plan, the S4 requirements and risk drafts,
and S2's planned interface (`worktree-org-io-create`, plan task T6):* S2
splits today's receive into `prepare_receive` → `PendingReceive` →
`apply_receive(rng, pending, chain_state: Option<OrgState>)` and keeps the

By ruling B (owner, 2026-10-06) org-node takes values and returns values: no
file, no endpoint, no keychain, no async once S2 has taken the chain read.
The five items below are what org-node offers org-io in place of the IO it
loses. The existing items they replace or narrow are amended in place in the
files that define them, with dated notes, by the task that changes the code
(plan §3.2, §3.3).

## The shape of the change, for an implementer

- **One store per Persona** (owner ruling, 2026-10-06). `StoreData` holds one
  `persona: PersonaRecord`, not a list; `OrgService` holds one `PersonaStore`
  per Persona and routes each operation to the store of the Persona it
  concerns. A Persona is bound to at most one Organisation (REQ-yp75u9), so
  that store also holds the Organisation's record, its provisional updates,
  the expectations its replies declared and the Invites it issued.
- **The device seed leaves the store.** `PersonaRecord.device_seed:
  DeviceSeed` becomes `device_key: DevicePublicKey`. The seed exists in
  org-node only as a `DeviceSecret`, moved in for one operation.
- **Sealed bytes out.** Every operation that changes a store returns a
  `#[must_use] StoreWrite { device_key, sealed }`; org-io writes `sealed` to
  that Persona's file. Ignoring it is a compile error once the workspace
  denies `unused_must_use` (`[workspace.lints.rust]` in the root
  `Cargo.toml`, added with the sealed store; today the workspace denies only
  three clippy lints).
- **One receive path by values.** `check_received(body)` then, after org-io's
  chain read, `commit_checked(checked, state)`.
- **The commit returns the bodies.** `commit_update` and `commit_checked`
  never send; `commit_update` returns every recipient's encoded body, built
  inside the commit with that commit's key.
- **The Invite comes back.** `invitation.rs` holds the Blobs, and the
  service records and settles outstanding invite identifiers in the store.

## The sealed Persona store

**SDD-asxwp8**: the sealed Persona store. Code: `org-node/src/store.rs` (`PersonaStore`, `SealedStore`, `StoreWrite`,
`StoreData`, `PersonaRecord`), and the routing in `org-node/src/service.rs`.
The store is the AEAD-sealed form of one Persona's data, keyed from that
Persona's device secret, given out as bytes and taken in as bytes.
traces: REQ-x3jrh8, REQ-qthum6, REQ-hzm4kt

**LLR-bg538c**: `PersonaStore::unseal(sealed: &SealedStore, device_key:
DevicePublicKey, secret: DeviceSecret) -> Result<PersonaStore, OrgNodeError>`
takes the secret by value and returns, from bytes `nonce(24) ‖ ciphertext`,
the store whose plaintext parses (LLR-8bum44) and whose `persona.device_key`
equals `device_key`; it refuses, with a distinct typed error each and without
panicking: fewer than 24 + 16 bytes (`StoreRefused(StoreRefusal::TooShort)`),
a ciphertext that does not authenticate under the derived key
(`StoreRefused(StoreRefusal::NotAuthentic)`), a plaintext that does not
decode or parse (`StoreRefused(StoreRefusal::Undecodable)` or the parse's
`InvalidField`), a secret whose Device public key is not `device_key`
(`DeviceSecretMismatch`, checked before any decryption), and a parsed
`persona.device_key` other than `device_key` (`DeviceSecretMismatch`). It
names no path and calls no `std::fs` function.
satisfies: REQ-x3jrh8

**LLR-2qqqx6**: the store key is the 32-byte output of HKDF-SHA-256 with the
device seed's 32 bytes as input keying material, the Device public key's 32
bytes as salt, and the info string `b"ods/persona-store/v1"`; it is held only
as the in-memory `XChaCha20Poly1305` of the open `PersonaStore`, never
serialised, never returned and never written. No Argon2 derivation and no
passphrase parameter remains anywhere in `org-node/src`.
satisfies: REQ-qthum6

**LLR-bvt5up**: every `OrgService` operation that changes a store
(`create_persona`, `create_organisation`, `commit_genesis`,
`discard_provisional`, `admit_member`, `revoke_member`, `commit_update`,
`commit_checked`, `expect_admission`, `build_invite`, `build_reply`,
`settle`) returns, beside its result, exactly one `StoreWrite { device_key,
sealed }` for the store it changed, sealed with a fresh 24-byte nonce after
the change; `StoreWrite` is `#[must_use]`; an operation that refuses returns
no `StoreWrite` and leaves the in-memory store as it was before the call.
Sealing uses the store key the open `PersonaStore` holds (LLR-2qqqx6): no
operation but `create_persona` and `PersonaStore::unseal` takes a
`DeviceSecret`, so saving a change to an open store never needs the keychain
(owner ruling, 2026-10-07). `PersonaRecord` holds `device_key:
DevicePublicKey` and no field of `StoreData` holds a device seed.
satisfies: REQ-x3jrh8, REQ-qthum6

*Amended 2026-10-08 before first merge (reconciled with S2, `e41cb09`, and
S3a's signing, plan §16.1):* "no operation but `create_persona` and
`PersonaStore::unseal` takes a `DeviceSecret`" also excepts the operations
that may sign S3a's acknowledgements (`commit_update`, `reconcile`,
`commit_checked`), which take a `device_secrets` closure called only on the
path that signs; an ordinary save still takes none. An operation that
empties its one-Persona store returns `StoreChange::Forgotten` in place of
the `StoreWrite` (LLR-6qjmhf's note). And since S2's `NodeBuilders` (org-io)
stands between the app and these operations, `create_persona`'s
`DeviceSecret` never reaches a caller of org-io's handle (plan task T3).

**LLR-rdda86**: `OrgService::new(stores: Vec<PersonaStore>)` holds one store
per Persona and refuses (`DuplicatePersonaStore`) two stores with the same
`device_key`; an operation naming a Persona or an Organisation reads and
changes only the store of that Persona, or of the Persona bound to that
Organisation, and leaves every other store unchanged in memory and unsealed;
`list_personas()` returns one record per store; a first admission is
committed only into a store that declared the expectation for its
Organisation and whose Persona's Device key the verified record lists.
satisfies: REQ-x3jrh8

*Note 2026-10-13 (S4, task T9):* `OrgService::restore_store(store)` puts
`store` in place of the held store with the same Device key, or adds it when
none is held. org-io uses it to reload a Persona from its file after a failed
write or removal. It seals nothing, changes no other store, removes no
store, and keeps one store per Device key. Its counterpart `drop_store`
removes one, and is LLR-jd82t6's. Test:
`restore_store_replaces_or_adds_one_store_and_drop_store_removes_one`
(sealed_store).

## SDD-72ddm6 — The node's own removal (S4 supersession)

**LLR-jd82t6**: `StoreData::forget_organisation` is called from exactly two
places: `revocation::accept` on success (LLR-r8qhky), and the one removal

  keychain write for a new Persona, and a failed reload after a failed
  store write or removal.
The `absences` test reads org-node's source for every other removal from
`orgs` or `stores`.

## The device secret

**SDD-fysk96**: the device secret. Code: `org-node/src/keys.rs` (`DeviceSecret`). The only form in which org-node
takes or gives a device ed25519 seed.
traces: REQ-26mjqa, REQ-y7tsft

**LLR-37k2s3**: `DeviceSecret` holds its 32 bytes in `zeroize::Zeroizing`,
so they are overwritten with zeros when it is dropped; it implements neither
`Clone`, `Copy`, `Display`, `Serialize` nor `Deserialize`; its `Debug` renders
exactly `DeviceSecret([REDACTED])`; its public operations are
`generate(rng)`, `from_keychain_bytes`, `device_key()` (the ed25519 verifying
key as a `DevicePublicKey`) and `lend_to_keychain`, and no public operation
returns its bytes, a reference to them or a `SigningKeypair`. `DeviceSeed`
and `SigningKeypair::device_seed` are removed.
satisfies: REQ-26mjqa, REQ-y7tsft

*Clarified 2026-10-15 (S4 review round 2, finding-3, PR-aa7prn):* "no public
operation returns its bytes" includes `lend_to_keychain`, whose return
carries no value derived from them (LLR-yp69jg, amended the same day). The
lend still hands its writer a reference for the writer's one call; what a
caller's own closure does with that reference inside the call is the
caller's code, as with any lend.

**LLR-yp69jg**: `DeviceSecret::from_keychain_bytes(bytes:
Zeroizing<Vec<u8>>) -> Result<DeviceSecret, OrgNodeError>` consumes the
buffer, refuses any length but 32 with `InvalidField { field: "device
secret", .. }` without echoing a byte, and copies the 32 bytes into the new
value before the buffer is dropped and zeroised;
`DeviceSecret::lend_to_keychain<R>(&self, write: impl FnOnce(&[u8; 32]) -> R)
-> R` calls `write` exactly once with the bytes and returns its result, and is
the only operation through which the bytes leave the value.
satisfies: REQ-26mjqa

*Amended 2026-10-15 (S4 review round 2, finding-3, PR-aa7prn):* the lend's
signature is `DeviceSecret::lend_to_keychain<E: std::error::Error>(&self,
write: impl FnOnce(&[u8; 32]) -> Result<(), E>) -> Result<(), E>`: `write` is
called exactly once with the bytes and its result is returned. The `<R>`
form above let a writer return the bytes themselves (`|seed| *seed`); a
result of `()` or an error bound to `std::error::Error`, which no byte array
implements, carries no value out, so the lend returns nothing derived from
the bytes (LLR-37k2s3).

*Corrected 2026-10-15 (S4 merge review, finding-1):* "carries no value out"
above claims more than the type gives. The bound stops `|s| *s` and
`|s| Err(*s)`, since no byte array is an error type; it does not stop a
caller-defined error type that wraps the bytes (`struct Carrier([u8; 32]);
impl std::error::Error for Carrier`, then `|s| Err(Carrier(*s))`). That
remaining case rests on review, as LLR-37k2s3's clarification of the same
day already says for what a closure captures. The one production caller,
org-io's `keychain.rs` (`entry.set_secret(seed)`), returns keyring's error.

*Clarified 2026-10-15 (S4 review round 2, finding-10):* the refusal's field
is `"Device seed"` (the text the code and its test use), not `"device
secret"` as written above; LLR-8bum44's form of `InvalidField` is unchanged.

**LLR-e5kqhg**: `OrgService::create_persona(rng, handle, name, surname) ->
Result<(PersonaId, DeviceSecret, StoreWrite), OrgNodeError>` draws a fresh
device seed as a `DeviceSecret`, opens a new store for the new Persona keyed
from it (LLR-2qqqx6), records the Persona with the secret's Device public key
and no seed, and returns the secret by value for org-io to write to the
keychain; org-node keeps no copy of it. `PersonaStore::unseal` consumes the
secret it is given and holds no copy of it after it returns.
satisfies: REQ-26mjqa, REQ-qthum6

## Outgoing message bodies

**SDD-bm27xt**: outgoing message bodies. Code: `org-node/src/service.rs` (`CommitOutcome`, `OutgoingMessage`), and the
renamed codec in `org-node/src/wire.rs` (SDD-kwncn7 keeps the codec; this
item is who receives what). Replaces `send_update`.
traces: REQ-6ehufy, REQ-3dsweu, REQ-szq3ud

**LLR-gdfqn9**: `commit_update(rng, org_id, chain_state: Option<OrgState>)
returns, beside its `StoreWrite`, a `CommitOutcome { org_id, epoch, root,
sender: PersonaId, outgoing: Vec<OutgoingMessage> }`, `OutgoingMessage {
recipient: DevicePublicKey, body: Vec<u8> }`; neither type is `Clone`, and
`OutgoingMessage`'s `Debug` renders the recipient and the body's length only,
never its bytes (an `OrgInformation` body carries the Organisation private
key, REQ-y7tsft). The bodies are built inside
the commit from the record as committed: one `OrgInformation` body (the
Envelope, the record snapshot as it stood before the commit, and the
Organisation private key the commit stored) for each Device the committed
record lists other than the sending Persona's own, in record order; then one
`Revocation` body (the Envelope alone) for each Device the record listed
before the commit and no longer lists, in record order. Each body is
`encode_message`'s output and within its bound. Building them writes no store
beyond the commit's own `StoreWrite` and sends nothing; `commit_genesis`
returns no recipients. A later commit cannot change a body already returned,
which resolves PR-gnh3j2 (owner ruling, 2026-10-07: S4 resolves it).
satisfies: REQ-6ehufy, REQ-3dsweu, REQ-szq3ud

*Amended 2026-10-07 before first merge (reconciled with S3a, `60c7d58`; plan
task T5):* a revocation body is `WireMessage::Revocation(notice)`, the
notice S3a's `notices_for` builds for that Device (its identity and an
absence proof from the committed record, LLR-kr5t6f, LLR-dc45ur), not the
Envelope. `CommitOutcome` keeps S3a's `acknowledgements`; S3a's
`revocations` field becomes those bodies. A commit that removes this node
returns its acknowledgements and no bodies, and `commit_update` takes the
same `device_secrets` closure as `commit_checked`, with a `StoreChange` in
place of the `StoreWrite`. The bodies are built in the commit step that
`commit_update` and `reconcile` share (LLR-fm38ww), so a commit found at
startup fans out the same bodies.
