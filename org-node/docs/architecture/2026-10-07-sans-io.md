## The shape of the change, for an implementer

- **One store per Persona** (owner ruling, 2026-10-06). `StoreData` holds one
  `persona: PersonaRecord`, not a list; `OrgService` holds one `PersonaStore`
  per Persona and routes each operation to the store of the Persona it
  concerns. A Persona is bound to at most one Organisation (REQ-yp75u9), so
  that store also holds the Organisation's record, its provisional updates,
  the expectations its replies declared and the Invites it issued.
- **The device seed leaves the store.** `PersonaRecord.device_seed:
  DeviceSeed` becomes `device_key: DevicePublicKey`. The seed exists in
  org-node only as a `DeviceSecret`, moved in for one operation.
- **Sealed bytes out.** Every operation that changes a store returns a
  `#[must_use] StoreWrite { device_key, sealed }`; org-io writes `sealed` to
  that Persona's file. Ignoring it is a compile error once the workspace
  denies `unused_must_use` (`[workspace.lints.rust]` in the root
  `Cargo.toml`, added with the sealed store; today the workspace denies only
  three clippy lints).
- **One receive path by values.** `check_received(body)` then, after org-io's
  chain read, `commit_checked(checked, state)`.
- **The commit returns the bodies.** `commit_update` and `commit_checked`
  never send; `commit_update` returns every recipient's encoded body, built
  inside the commit with that commit's key.
- **The Invite comes back.** `invitation.rs` holds the Blobs, and the
  service records and settles outstanding invite identifiers in the store.

## The sealed Persona store

**SDD-asxwp8**: the sealed Persona store. Code: `org-node/src/store.rs` (`PersonaStore`, `SealedStore`, `StoreWrite`,
`StoreData`, `PersonaRecord`), and the routing in `org-node/src/service.rs`.
The store is the AEAD-sealed form of one Persona's data, keyed from that
Persona's device secret, given out as bytes and taken in as bytes.
traces: REQ-x3jrh8, REQ-qthum6, REQ-hzm4kt

**LLR-bg538c**: `PersonaStore::unseal(sealed: &SealedStore, device_key:
DevicePublicKey, secret: DeviceSecret) -> Result<PersonaStore, OrgNodeError>`
takes the secret by value and returns, from bytes `nonce(24) ‖ ciphertext`,
the store whose plaintext parses (LLR-7yu2xy) and whose `persona.device_key`
equals `device_key`; it refuses, with a distinct typed error each and without
panicking: fewer than 24 + 16 bytes (`StoreRefused(StoreRefusal::TooShort)`),
a ciphertext that does not authenticate under the derived key
(`StoreRefused(StoreRefusal::NotAuthentic)`), a plaintext that does not
decode or parse (`StoreRefused(StoreRefusal::Undecodable)` or the parse's
`InvalidField`), a secret whose Device public key is not `device_key`
(`DeviceSecretMismatch`, checked before any decryption), and a parsed
`persona.device_key` other than `device_key` (`DeviceSecretMismatch`). It
names no path and calls no `std::fs` function.
satisfies: REQ-x3jrh8

**LLR-2qqqx6**: the store key is the 32-byte output of HKDF-SHA-256 with the
device seed's 32 bytes as input keying material, the Device public key's 32
bytes as salt, and the info string `b"ods/persona-store/v1"`; it is held only
as the in-memory `XChaCha20Poly1305` of the open `PersonaStore`, never
serialised, never returned and never written. No Argon2 derivation and no
passphrase parameter remains anywhere in `org-node/src`.
satisfies: REQ-qthum6

## The device secret

**SDD-fysk96**: the device secret. Code: `org-node/src/keys.rs` (`DeviceSecret`). The only form in which org-node
takes or gives a device ed25519 seed.
traces: REQ-26mjqa, REQ-y7tsft

**LLR-37k2s3**: `DeviceSecret` holds its 32 bytes in `zeroize::Zeroizing`,
so they are overwritten with zeros when it is dropped; it implements neither
`Clone`, `Copy`, `Display`, `Serialize` nor `Deserialize`; its `Debug` renders
exactly `DeviceSecret([REDACTED])`; its public operations are
`generate(rng)`, `from_keychain_bytes`, `device_key()` (the ed25519 verifying
key as a `DevicePublicKey`) and `lend_to_keychain`, and no public operation
returns its bytes, a reference to them or a `SigningKeypair`. `DeviceSeed`
and `SigningKeypair::device_seed` are removed.
satisfies: REQ-26mjqa, REQ-y7tsft

*Clarified 2026-10-15 (S4 review round 2, finding-3, the resolved problem report on the lend returning the seed bytes):* "no public
operation returns its bytes" includes `lend_to_keychain`, whose return
carries no value derived from them (LLR-yp69jg, amended the same day). The
lend still hands its writer a reference for the writer's one call; what a
caller's own closure does with that reference inside the call is the
caller's code, as with any lend.

**LLR-yp69jg**: `DeviceSecret::from_keychain_bytes(bytes:
Zeroizing<Vec<u8>>) -> Result<DeviceSecret, OrgNodeError>` consumes the
buffer, refuses any length but 32 with `InvalidField { field: "device
secret", .. }` without echoing a byte, and copies the 32 bytes into the new
value before the buffer is dropped and zeroised;
`DeviceSecret::lend_to_keychain<R>(&self, write: impl FnOnce(&[u8; 32]) -> R)
-> R` calls `write` exactly once with the bytes and returns its result, and is
the only operation through which the bytes leave the value.
satisfies: REQ-26mjqa

*Amended 2026-10-15 (S4 review round 2, finding-3, the resolved problem report on the lend returning the seed bytes):* the lend's
signature is `DeviceSecret::lend_to_keychain<E: std::error::Error>(&self,
write: impl FnOnce(&[u8; 32]) -> Result<(), E>) -> Result<(), E>`: `write` is
called exactly once with the bytes and its result is returned. The `<R>`
form above let a writer return the bytes themselves (`|seed| *seed`); a
result of `()` or an error bound to `std::error::Error`, which no byte array
implements, carries no value out, so the lend returns nothing derived from
the bytes (LLR-37k2s3).

*Corrected 2026-10-15 (S4 merge review, finding-1):* "carries no value out"
above claims more than the type gives. The bound stops `|s| *s` and
`|s| Err(*s)`, since no byte array is an error type; it does not stop a
caller-defined error type that wraps the bytes (`struct Carrier([u8; 32]);
impl std::error::Error for Carrier`, then `|s| Err(Carrier(*s))`). That
remaining case rests on review, as LLR-37k2s3's clarification of the same
day already says for what a closure captures. The one production caller,
org-io's `keychain.rs` (`entry.set_secret(seed)`), returns keyring's error.

*Clarified 2026-10-15 (S4 review round 2, finding-10):* the refusal's field
is `"Device seed"` (the text the code and its test use), not `"device
secret"` as written above; LLR-7yu2xy's form of `InvalidField` is unchanged.
