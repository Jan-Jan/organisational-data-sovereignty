# Risk assessment of the app's derived low-level requirements

The app's first architecture ledger
(`app/docs/architecture/2026-10-05-decomposition.md`,
this change) writes forty-six low-level requirements. Thirty-three refine a
high-level requirement that the risk register has already assessed, and they
inherit that assessment unchanged. **Thirteen are `satisfies: derived`**: they
record behaviour that no requirement demands. ISO 14971 asks that such
behaviour be assessed rather than assumed harmless, and this file is that
assessment.

Counted 2026-10-05 against the draft: `grep -c '^\*\*LLR-'` is 46 and
`grep -c '^satisfies: derived'` is 13. Recounted after review round 2
(finding-4): review round 1 added LLR-uus6ar, which refines REQ-cj5jmx.

The hazards named below are those of `app/docs/risk/2026-09-14-app-hazards.md`
§4, with the method and the acceptability matrix of that file and of
`app/docs/risk/README.md`. **No new hazard and no new risk control** is
introduced. Each section says why, and where a derived requirement pins
behaviour that an open problem report calls a defect, it names the report.

## The transport mode's parsing

assesses: LLR-j5pacp

Assessed against **HAZ-n97v5g**. A misspelled `ODS_TRANSPORT`, such as
`LOOPBACK` or `loop back`, yields Networked, silently. The mode the service
runs in and the mode it reports come from the same value (LLR-8tzbzn,
RC-8ygnjd), so the revoke form's peer-address precondition (RC-jrkn7w, through
REQ-vgr7s2) matches what the service does. An operator who meant Loopback is
shown Networked in the status bar. The mapping adds no path to the hazard's
harm. It is the behaviour the register was assessed against, which
`transport_mode_from` was written to preserve exactly.

## Where the persona store is opened, and what is refused

assesses: LLR-85zque

Assessed against **HAZ-8ghmhn** and **HAZ-ny7yvt**, whose controls (RC-xt4qr3,
RC-djzms3) decide the passphrase and the directory. This requirement is the
step after that decision: it opens the store at a fixed name inside the
decided directory, and refuses rather than substituting. It does not create a
fresh store when the existing one will not open under the passphrase, so key
material is neither relocated nor silently abandoned. A refusal reaches the
operator as a panic at startup; that is PR-w5dae4's, and is unchanged. No new
hazard.

## The handler's own member-identifier check

assesses: LLR-6pmrma

Assessed against **HAZ-n97v5g**: could this check block a revocation that the
form accepts? The form (REQ-he8ejb, LLR-csbs5v) trims the identifier and strips
one `0x`. Revoke.svelte sends the trimmed value, and the handler strips the same
single prefix, so a member identifier the form accepts is one the handler
accepts. The handler refuses only malformed identifiers, as defence in depth.
It does not normalise them into a different member. No new hazard.

## Decoding the revocation's peer address

assesses: LLR-n6twt7

Assessed against **HAZ-n97v5g**. In Networked transport the form permits an
empty address, which the handler treats as absent (LLR-ty85xv, REQ-vgr7s2). A
supplied address that does not decode is refused rather than dropped. That
an address that decodes is the one handed to the service is read from the
code. The falsifiability sweep cut it from the requirement, because no gated
test reaches the service's use of it. A refusal is visible on the form and
leaves the operator able to correct the address. The repeated `0x` strip on
this value is PR-5mc4d8's, and this requirement deliberately does not state
it. No new hazard.

## The admission's Organisation secret

assesses: LLR-8krgzj

Assessed against **HAZ-8ghmhn**'s family: key material crossing a boundary.
The secret is parsed to exactly thirty-two bytes or refused. It is never
truncated or padded into a different secret. That the parsed secret is the one
handed to the service is not part of the requirement: the falsifiability sweep
cut it, because no gated test reaches the service's use of it. That step is
read from the code, not shown by a test. Admit.svelte always sends none
today, so the parsed branch is reachable only over IPC. The repeated `0x`
strip is PR-5mc4d8's. No new hazard.

## The admission's peer address

assesses: LLR-ctrfz4

Assessed against **HAZ-n97v5g** and the admission path. A join request with no
node address is not refused. The code dials it by its device key, as the
Networked design requires, but the falsifiability sweep cut that from the
requirement, because no gated test reaches the dial. One with an address that
does not decode is refused, not admitted to an unreachable or substituted
address. Whether a Networked join request carries an address is a premise of
REQ-vgr7s2 that PR-7zz76t books as false. This requirement holds either way.
No new hazard.

## Parsing a Persona's details at the boundary

assesses: LLR-p7dfxb

Assessed with **no hazard**. The parse is org-node's own (its requirement is
not exported to this unit), and the handler adds only the field name to the
refusal. Nothing is created on a refusal. The details identify a persona to
its operator, and the identity binding on the membership pathway is the
member key, not these fields.

## A closed command list

assesses: LLR-4wcyqy

Assessed against **HAZ-n97v5g**'s pathway, a command that silently does
nothing. A misnamed invocation is refused, so a frontend wrapper whose name
drifts from the handler fails visibly rather than resolving undefined. This
requirement removes a silent-failure path and adds none.

*Corrected 2026-10-05 (review round 1, finding-4).* The paragraph above
credited the tests with the product's behaviour, and they showed only the IPC
suite's. The suite registers its own copy of the handler list, so deleting a
command from `lib.rs` left every test green. What is gated now: the suite's
list refuses an unregistered name, and
`product_registers_the_same_commands_as_the_harness` requires `lib.rs`'s
`generate_handler!` list to name the same commands as the suite's. Together
these give the product the behaviour the paragraph claims. The test compares
names, not registration order or the attributes on each handler. Since review
round 2 (finding-2) it also requires exactly one `generate_handler!` and one
`invoke_handler` call in `lib.rs`, outside `//` comments, because Tauri keeps
only the last handler registered. It reads no block comments or string
literals. Assessment unchanged: no new hazard.

## What a persona carries across IPC

assesses: LLR-pguhw5

Assessed against **HAZ-8ghmhn**'s family: the confidentiality of key
material. The persona object that crosses into the webview has exactly six
fields and no seed. That bounds what a script in the webview could read
through `list_personas`. This matters more since HAZ-e2zupz showed that a
script there can call every command. No new hazard: the requirement narrows
an exposure and opens none.

## Decoding a join request for display

assesses: LLR-pmus9f

Assessed against the admission path. The decoded request is shown to the
administrator before admission and stores nothing. The keys it returns are
public keys. A blob that does not decode is refused. The truncation of those
keys in Admit.svelte is a display concern of the onboarding panels, which
carry no low-level requirement (SDD-6g3wnh) and are booked to the Gap-20
change. No new hazard.

## The three events of a verified update

assesses: LLR-p2nm5a

Assessed against **HAZ-9fmhm4** and **HAZ-5ha5vv**. Each value is the measured
one, epoch 0 included, so no sentinel reaches the display (HAZ-5ha5vv). But
`membership-updated` and `incoming-verified` carry the same update, and
Membership.svelte files both as verification rows, so one verified update is
shown as two. That overstates the count of verifications, which is HAZ-9fmhm4's
territory. It is not new: it is booked as PR-bu6mau, and that report carries
the hazard note. This requirement records the mapping as it is and does not
make the duplicate a requirement of the display.

## The placeholder for an unnamed organisation

assesses: LLR-mzae5q

Assessed against **HAZ-9fmhm4**. A failure that names no organisation is shown
as `(unknown organisation)` rather than `null`. Every such failure today is
unnamed (LLR-7bk6qh), so the row cannot say which organisation failed. That is
PR-j9f6kk's item 1, open and unchanged. The requirement records today's
behaviour, and the row's outcome stays "not verified" (REQ-a83vqr). No new
hazard.

## The two list limits

assesses: LLR-rzx6ks

Assessed against **HAZ-9fmhm4**, through the verification log as the
operator's record. The log keeps the newest 50 rows and the error list the
newest 20. Older entries are dropped from the view and are not persisted
anywhere, so a burst of more than 50 verifications hides the earliest from the
operator. The register already identifies this as unminted control 11 of its
§8 ("a display cap rather than a retention policy"), and it stays unminted.
The bound protects the webview's memory, and the log is not the system of
record: the chain is. The bound was in the code the register was assessed
against; this requirement only makes it gated. No new hazard.
