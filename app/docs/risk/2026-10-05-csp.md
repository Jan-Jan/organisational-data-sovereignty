# Hazard analysis — the webview runs with no Content-Security-Policy

One hazard, added by owner ruling 4 of
`docs/plans/2026-10-05-app-architecture.md` ("Add a CSP"). The scope, method
and harm pathway are those of `app/docs/risk/2026-09-14-app-hazards.md` §1–§2;
the acceptability matrix is in `app/docs/risk/README.md`.

## 1. The hazard

**HAZ-e2zupz**: A webview that runs with no Content-Security-Policy while every
one of the twelve Tauri commands is reachable from it through `core:default`
IPC with no per-command permission, where script that reaches the webview from
anywhere other than the bundled code (an injected inline script, a remote
script load, or `eval` of attacker-shaped text) calls `revoke_member`,
`admit_member` or `import_join_request` in the administrator's name, or sends
what it reads to a remote origin, so a member who should hold access is
removed, someone who should not is admitted, and the organisation's documents
reach a person they identify a source to. Severity: S3. Probability: P1.

**Where it begins.** `tauri.conf.json` sets `app.security.csp: null`. The
webview then applies no policy of its own: inline script runs, `eval` runs,
script and connections to any origin are allowed. `capabilities/default.json`
grants `core:default` to the main window, and the twelve commands registered in
`lib.rs` carry no permission of their own, so whatever runs in the window may
invoke every one of them.

**Where it ends.** At the command handler. Nothing between the webview and
`OrgService` asks whether the call came from the user's intent. A `revoke_member`
that script issues is the same call the Revoke panel issues.

**Severity S3.** The harm pathway is the register's own (§2): an admission or a
revocation the administrator did not intend, or a document sent to the wrong
reader, reaches the people the deployments protect. The command surface is the
whole membership authority of the installation.

**Probability P1, and why it buys nothing.** No route for foreign script into
the webview is known today. The frontend renders no HTML from data (no
`{@html}`, no `innerHTML` in `app/src`), Svelte escapes text, and the bundle is
served from the app's own origin. The routes that remain are a dependency
compiled into the bundle, a future rendering sink, and a webview defect. The
SOUP inventory records a high advisory against a shipped package (devalue
5.8.1), which is the class of route this hazard is about. At S3 the matrix
makes the risk unacceptable at every probability, so P1 decides nothing.

## 2. The control

**RC-mq2365**: Ship the webview with a Content-Security-Policy that admits
script only from the application's own origin, with no inline or evaluated
script, forbids plugins, base-URI changes, framing and form submission, and
permits connections only to Tauri's IPC endpoints, so script that did not come
from the bundle cannot run and data cannot leave through the webview.
mitigates: HAZ-e2zupz

Realised by REQ-cj5jmx.

**ISO 14971 priority.** This is a protective measure: the commands stay
reachable from the window, and the policy keeps foreign script from running in
it. Inherent safety by design would remove the reach itself: a capability per
command, or a frontend that cannot issue `revoke_member` without a gesture the
script cannot forge. That is not minted here (see §4).

**What the control does not stop.** Script served from `'self'` is allowed by
design, and the bundle is `'self'`. A compromised package compiled into the
bundle is therefore not stopped by this control. What it does stop is that
package, or an injected string, loading more code from the network or sending
data out of the webview.

**What this control breaks, and the analysis of each.**

1. **The bundle's inline bootstrap script.** SvelteKit's static adapter writes
   an inline `<script>` into `index.html`, and `script-src 'self'` forbids
   inline script. Tauri computes hashes of the bundle's inline scripts at build
   time and appends them to `script-src`, so the bundle should still load. If
   it does not, the window is blank. No command can be invoked from a blank
   window, so nothing is admitted or revoked by mistake. But the administrator
   also cannot revoke, and a revocation that cannot be submitted is the
   register's central harm. The failure is loud: it shows at first launch, on
   every launch, before any membership action. It is caught by the owner's
   smoke test before the squash (§3). No separate hazard is minted for it,
   because it cannot occur silently in a deployed build that passed that test.
2. **`style-src 'unsafe-inline'`.** It is kept, because Svelte and Tauri write
   style attributes. Injected style cannot invoke a command or open a
   connection; with `img-src 'self' data:` and `connect-src` restricted, it
   also has nowhere to send data. No new hazard.
3. **Development mode.** `npm run tauri dev` loads the frontend from the Vite
   server at `localhost:5173`. That origin is allowed only in `devCsp`, which
   Tauri applies in development builds alone. The shipped `csp` names no
   localhost origin, and a test asserts it. No new hazard in the shipped build.
   If the dev server's own inline scripts need more than `devCsp` allows, the
   window is blank in development. That costs the developer time and is not a
   hazard.

## 3. Verification, and its limitation

`app/src-tauri/tests/csp_policy.rs` reads `tauri.conf.json`, parses
`app.security.csp` and `devCsp` into directives, and checks every clause of
REQ-cj5jmx. The test also proves that its checker rejects each weakening the
requirement forbids. It is in the unit's cargo `verify_commands` line.

Review round 1 added two checks. The shipped policy may name no directive
outside an allow-list (LLR-uus6ar), so a weaker directive that overrides a
fallback, such as `script-src-elem 'unsafe-inline'`, is refused rather than
ignored. And `devCsp` is compared with `csp` directive by directive
(LLR-tc5aax): it must equal it except that `script-src` and `connect-src`
each add exactly the dev-server origins.

**Verification limitation.** Nothing in the gate shows that the bundled app
still loads and works under the policy. The test checks the configuration, not
the webview that applies it. Two facts are outside its reach: the hashes Tauri
appends to `script-src` at build time, and whether IPC on each platform uses
only `ipc:` or `http://ipc.localhost`. This is the owner's smoke test, to be
run before the squash:

    npm --prefix app run tauri build

Launch the bundle and exercise one command, for example the connection status
bar. A blank window or an IPC error on the console is a failure.

## 4. Residual risk

**Residual risk: S3 / P1. UNACCEPTABLE.** Script that does not come from the
bundle can no longer run in the webview, and data can no longer leave it. The
probability stays at P1 rather than lower, because script that does come from
the bundle still reaches all twelve commands. As for every S3 entry in this
register, the matrix allows no residual at S3, and this one is recorded as
unacceptable. It has not been accepted. The owner confirmed the S3 and P1
ratings and the protective-measure classification on 2026-10-05. The next
reduction is the inherent-safety control below.

**Not minted here: the inherent-safety control.** Restrict each command to a
Tauri capability that names it, so that `core:default` no longer implies
`revoke_member`. Even then, script from `'self'` holds the main window's
capabilities, so this narrows the surface without closing it. It is a design
change to the IPC boundary, and it belongs with the deviation item T3 books for
the startup wiring.

## 5. Derived requirements assessment

REQ-cj5jmx is `satisfies: derived`. It exists because this analysis demanded
RC-mq2365, not because of a system need. It introduces no new hazard. Its only
side effect is the blank-window failure analysed in §2 item 1, which is loud,
reaches no command, and is caught by the smoke test before the change merges.
It strengthens the control of no other hazard in the register and weakens none.

assesses: REQ-cj5jmx
