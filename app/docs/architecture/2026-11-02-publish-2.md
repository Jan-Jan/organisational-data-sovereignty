# Design — the removed Devices view (app)

Software item and low-level requirements for change
`worktree-org-io-publish-2`, task T13b of
`docs/plans/2026-10-16-org-io-publish-2.md` (§0; plan task T16g), drafted
2026-11-03 before any code, against master `7ac0825`. They refine
`app/docs/requirements/2026-11-02-publish-2.md`. Class C, no per-item
override; no new dependency edge or SOUP.

## Choices made (architecture, three options considered)

When the webview reads the list again:

1. **When the panel is shown, on the user's Refresh, and after each
   `verification-result` for the Organisation** (chosen). No new event:
   LLR-2vg79y keeps announcing a received acknowledgement by no event, and
   periodic verification (REQ-5q7nyg, default 10 minutes) bounds how stale
   the panel gets.
2. A new `acknowledgement-received` event, the panel re-reading on it.
   Rejected for now: it supersedes LLR-2vg79y and its six green tests for a
   panel the Admin opens by hand; it can be added later without changing
   this design.
3. Carry the removed Devices on `list_orgs`' `OrgDto`. Rejected: every
   Organisation listing would read them, and `OrgDto` is SDD-6pjvhc's
   general DTO, not this view's.

## The IPC command (SDD-6pjvhc)

**LLR-ce4hxz**: the IPC suite's handler list registers exactly these
eighteen commands under their snake_case names: `propose_person`,
`propose_founding_organisation`, `issue_invite`, `read_invite`,
`propose_member`, `request_admission`, `propose_admission`,
`propose_revocation`, `cancel_invite`, `propose_updated_organisation`,
`write_organisation_to_chain`, `verify_organisation`,
`list_admission_requests`, `list_removed_devices`, `list_personas`,
`list_orgs`, `connection_status` and `start_receiver`; an invocation of any
other name, `send_organisation`, `request_organisation`,
`reconcile_organisations`, `produce_invite_reply`, `import_invite_reply`,
`admit_member` and `revoke_member` included, is refused rather than
answered; and the `generate_handler!` list in `app/src-tauri/src/lib.rs`
names the same set, in exactly one `generate_handler!` list in exactly one
`invoke_handler` call.
satisfies: derived
supersedes: LLR-kk8gc7

LLR-kk8gc7's rule, with `list_removed_devices` joining the set: eighteen,
not seventeen.

**LLR-dmfvv6**: `list_removed_devices` takes `org_id`, parses it at the IPC
edge as every Organisation identifier is parsed there (a malformed one is
refused with the parse's text, org-io not called), calls org-io's
`OrgIo::removed_devices(org_id)` once and returns, in org-io's order, one
`RemovedDeviceDto { member_id, device_key, acknowledged_epoch }` per entry —
`member_id` and `device_key` lowercase hex, `acknowledged_epoch` the epoch
as a number or `null` — carrying no key material other than the public
DevicePublicKey; an org-io refusal is returned as its text.
satisfies: REQ-yvzef9

## The removed Devices view

**SDD-g9ugu7**: the removed Devices view: it shows the Admin, in the
"Removed Devices (Admin)" panel, each Device an Organisation's store holds
as revoked. Code: `app/src/lib/removed.ts` (the pure wording), the
`RemovedDevices.svelte` component shown with the Revoke panel (with the
re-read decision), and `listRemovedDevices` in `app/src/lib/api.ts`. It
decides nothing about acknowledgements: org-io lists, the view words.
traces: REQ-yvzef9

**LLR-cs9bmw**: the panel is titled `Removed Devices (Admin)` and always
shows the statement `An acknowledgement is the removed Device's own signed
statement that it acted on its removal. It is not proof that its data was
deleted.`; for each `RemovedDeviceDto` it shows one row with the MemberId
and the DevicePublicKey and, from `removedDeviceLine(dto)`, `acknowledged
its removal at epoch N` when `acknowledged_epoch` is `N`, else `no
acknowledgement received by this Device`; an empty list shows `No removed
Devices.`; a refusal shows its text. No text the panel shows contains
"deleted", "erased" or "wiped" except the statement's "not proof that its
data was deleted".
satisfies: REQ-yvzef9

**LLR-x9qbhu**: the panel calls `listRemovedDevices(orgId)` once when it is
shown for an Organisation, once on each click of its `Refresh` button, and
once after each `verification-result` event whose `org_id` is that
Organisation; a `verification-result` for another Organisation, and any
other event, reads nothing. Each answer replaces the rows shown.
satisfies: REQ-yvzef9

*Amended 2026-11-09 (change `worktree-org-io-publish-2`, merge review round

*Amended 2026-11-09 (change `worktree-org-io-publish-2`, merge review round
1, MR1-A3):* "each answer replaces the rows shown" holds for the answer to
