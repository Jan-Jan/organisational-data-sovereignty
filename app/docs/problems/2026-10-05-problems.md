# Problem reports — the `app` unit, opened by the 2026-10-05 architecture change

Five anomalies, found while decomposing the unit and writing its low-level
requirements (`docs/plans/2026-10-05-app-architecture.md`). They are booked,
not fixed, under owner ruling 2 of that plan (2026-10-05). Each one is pinned by
a test that asserts today's behaviour where the existing harness reaches it.
Where none does, the report says why.

The plan's other two findings, the `receiverStarted` race and the event loss on
a tab switch, share PR-h6xpnh's root cause. They are an addendum to PR-h6xpnh
in `2026-09-14-app-problems.md`, not new reports.

---

**PR-8vh53d**: The npm lock pins `devalue` 5.8.1, a runtime dependency of the
SvelteKit client, which `npm audit` reports under seven advisories, three of
them high.
affects: RC-mq2365, SDD-6g3wnh
opened: 2026-10-05
status: open

`npm audit --prefix app` lists `devalue` 5.8.1 as high, with advisories
including GHSA-j22f-vq7h-c4qm (`stringify`/`uneval` serialise shared memory,
high), GHSA-mcm9-63f2-9j32 and GHSA-x5rw-q4pp-hg5g (high), and
GHSA-9rgm-9g3h-6x36 (moderate). A fix is available. The package is flagged
`dev` in the lock, so `npm audit --omit=dev` reports nothing. The `dev` flag
does not mean unshipped (`app/docs/architecture/soup.md`): `@sveltejs/kit`'s
client runtime imports `devalue` (`src/runtime/client/client.js`), and that
runtime is compiled into `build/`, which Tauri embeds.

**Measured on 2026-10-05, at this change's T3 tip.** `npm run build` succeeds,
and none of `devalue`'s error strings appear in `build/` ("Cannot stringify",
"Invalid ArrayBuffer encoding", "Invalid circular reference", "Unknown type").
Kit's production uses are `devalue.unflatten` for server-data streams, which a
prerendered `ssr = false` app does not fetch, and two `devalue.stringify`
calls that run only under `DEV`. So the current bundle appears to tree-shake
`devalue` out. That is a fact about this build, not a control. Any change that
starts using server data or snapshots brings the vulnerable version into the
shipped bundle, and no gate in this unit would notice.

The advisory is the class of route HAZ-e2zupz is about: script reaching the
webview through a dependency compiled into the bundle. RC-mq2365's policy
bounds what such script could do. It does not remove the dependency.

**No pin.** No gated test reaches a dependency advisory. The unit has no audit
step in `verify_commands`, and a test asserting "5.8.1 is locked" would pin a
version, not a behaviour. Closing this means upgrading past 5.9.2 and adding an
advisory scan to the gates. The scan is the gap the SOUP inventory records.

**PR-cu2h2g**: When one `listen` call rejects, `subscribeAll` rejects without
cancelling the listeners that had already registered, so they stay attached to
a view that never received a cleanup.
affects: REQ-rq8g2v, LLR-z4ky6f
opened: 2026-10-05
status: open

`app/src/lib/receiver.ts:17-19` awaits `Promise.all` over the subscriptions.
`Promise.all` rejects on the first failure and discards the `UnlistenFn`s of
the subscriptions that resolved. The function then rejects, so the caller gets
no cleanup. Nothing holds those `UnlistenFn`s, so nothing can cancel the
listeners. `Membership.svelte` and `Revoke.svelte` attach only a `.then` to
the promise, so the rejection is also unhandled.

REQ-rq8g2v says "unsubscribe exactly the event listeners it registered". The
listeners leaked here were registered, and they are never unsubscribed.
LLR-z4ky6f says that on a failure `subscribeAll` rejects with that failure, and
it does not claim the rest. The decomposition records the gap there. The
consequence is PR-u34uqm's: live handlers bound to a destroyed component, one
more set per visit to the tab, so duplicate rows in the verification log
(HAZ-9fmhm4). It needs a `listen` that rejects, which Tauri's `listen` can do
when its own IPC call fails. That is rarer than PR-u34uqm's race.

**Pin.** `app/tests/receiver.subscribe.test.ts`, "leaves a registered listener
attached when another registration fails (PR-cu2h2g)" (verifies: PR-cu2h2g).
It asserts today's behaviour: after the rejection, the registered listener's
cleanup has not been called. The fix must turn it around.

**PR-uxj7bg**: When the connection-status fetch fails, the Revoke panel keeps
its initial `'networked'` transport mode, so in a Loopback installation it
submits a revocation with no peer address.
affects: REQ-vgr7s2, REQ-645jq9, LLR-c9r5uf, SDD-6g3wnh
opened: 2026-10-05
status: open

`app/src/lib/components/Revoke.svelte:45` starts `transportMode` at
`'networked'`, and `loadTransportMode` (`:62-68`) swallows a failed
`connectionStatus()` and keeps that value. `validateRevokeInput` then applies
the Networked rule (LLR-c9r5uf) and accepts an empty peer address. That is the
decision REQ-vgr7s2 forbids in Loopback. The panel does not know the mode, and
it acts as if it did. The comment says the status bar reports the failure, but
nothing on the Revoke panel does.

Read from `org-node/src/service.rs`, not run: `revoke_member` submits the chain
update (line 1129) before the Loopback branch refuses a missing address (lines
1172-1176), and it saves the store (around line 1203) only after the send. So
the operator sees an error for a revocation that has already reached the chain,
the revoked member is not notified, and the local record is not saved. That
divergence is org-node's ordering. This report covers only the app's half: the
panel guessing the mode.

**No pin.** The defect is in the component's state handling, and no gated test
mounts a Svelte component (SDD-6g3wnh). `validateRevokeInput` behaves correctly
for the mode it is given. The wrong input reaches it from code the harness does
not run.

**PR-bu6mau**: One verified update is shown as two ✓ rows in the verification
log, because the backend announces it as both `membership-updated` and
`incoming-verified` and the frontend files each as a row.
affects: LLR-p2nm5a, LLR-53hayh, SDD-mwqf6x, SDD-8jw9mn
opened: 2026-10-05
status: open

`app/src-tauri/src/events.rs:194-207` maps `ReceiverOutcome::Updated` to
`membership-updated`, then `incoming-verified`, with identical payloads, then
`epoch-changed`. `Membership.svelte` subscribes `recordVerified` to both of the
first two, and each call adds a verified row through `applyReceiverEvent`.

Hazard note: HAZ-9fmhm4. The log overstates the number of verifications by a
factor of two. It cannot show ✓ for an update that did not verify, so it does
not reopen the hazard's main harm. But an operator counting rows against the
updates they expect sees twice as many, and that disagreement is what makes a
real divergence harder to spot. The derived-risk draft's assessment of
LLR-p2nm5a refers here.

**Pin.** `app/src-tauri/tests/receiver_events.rs`,
`updated_emits_membership_incoming_and_epoch` (verifies: LLR-p2nm5a, PR-bu6mau).
It already asserts both event names for one outcome. Removing or renaming
either reddens it. The frontend half, two subscriptions to one handler, is in
`Membership.svelte`, which no gated test mounts (SDD-6g3wnh).

**PR-7zz76t**: REQ-vgr7s2's rationale, and HAZ-n97v5g's wording, rest on the
premise that a Networked join request never carries a node address. org-node
puts an address in every join request exported while an endpoint is bound,
whatever the transport mode.
affects: REQ-vgr7s2, LLR-c9r5uf, LLR-ctrfz4
opened: 2026-10-05
status: open

`org-node/src/service.rs:723-728`, `export_join_request`: when
`self.endpoint` is bound, `node_addr` is the postcard encoding of
`ep.node_addr_for_dial()`. The mode is never consulted. An endpoint is bound
lazily by `ensure_endpoint`, which runs on the first admit, revoke or receive,
including the receiver loop. So a persona that has started its receiver
exports a join request with an address in Networked mode too. It exports one
without an address only before any endpoint is bound.

REQ-vgr7s2's own behaviour still holds: Networked revocation dials by the
device key and ignores any peer address (`service.rs` `revoke_member`'s
contract). LLR-ctrfz4's admission decodes an address when one is present. What
is false is the justification, "a join request carries no `node_addr`, so ...
the operator has nothing to paste", and the matching clause in HAZ-n97v5g's
hazardous situation. A requirement whose premise is wrong gives the wrong
guidance to whoever amends it next. Closing this means correcting the rationale
and the hazard text, or making org-node's behaviour match the premise. Either
is a requirement decision.

**No pin.** The behaviour is org-node's. An app test would have to bind an
endpoint through `AppState::for_test` (it installs `ChainNotConfigured`) and
export a join request. `export_join_request` is reachable only as a fixture
(SDD-6g3wnh), and the harness binds no endpoint. A pin in org-node's tests
would have to carry an annotation naming another unit's problem report.
